> 调研日期:**2026-10-17** · 目标:为「FastAPI + Redis + Celery + PostgreSQL 接口自动化测试平台」寻找可借鉴的实现

## 2. 结论摘要

1. **没有任何主流高星项目是 FastAPI + Celery + Redis + PostgreSQL。** 最接近的两个完整匹配(zerorunner、TestersStageV2)都用 MySQL;星数最高的 FastAPI 测试平台 pity 用的是 APScheduler 而非 Celery。**这套组合是真空白,我们是从零件组装,不是克隆参照物。**

2. **中文 FastAPI 测试平台的惯例高度一致,值得跟随**:后端 `FastAPI + SQLAlchemy 2 (async) + Celery + Redis`,前端 `Vue 3 + Element Plus + Pinia + Vite`。调研中每一个打开前端清单的 FastAPI 平台都是 Vue3 + Element Plus。

3. **PostgreSQL 的替换路径是已知且已被走通的**。pity、ApiPulse、ntest、BrickCoreTest 都同时携带 `asyncpg` / `psycopg2`,说明从 MySQL 换到 PG 不需要架构改动。

4. **存在两代平台,老一代是维护陷阱**。Django/Flask + Celery 那一代(AnotherFasterRunner 已**归档**、FXTest、TestRunner、teprunner)和 FastAPI 这一代。`AnotherFasterRunner` 与 `Sonic` 已明确归档;`YApi`、`RunnerGo`、`LuckyFrameWeb` 均已停更(2024 年或更早)。

5. **大平台不是代码参考**。MeterSphere(13.5k★)是 Java/Spring Boot + Kafka + JMeter,且许可为**非标准许可**(GitHub 报告 `NOASSERTION`,另有付费企业版)—— 架构上极有启发,但不能复用代码。RunnerGo 是拆成六个仓库的 Go 微服务。

6. **客户端工具是 UI/UX 参考,不是架构参考**。Hoppscotch(80.6k★)、Bruno(47.7k★)、Newman、Hurl 都是客户端或 CLI,没有服务端和数据库,不能作为平台架构的参照。

## 4. 重点项目的深入分析

### 4.1 zerorunner — 最接近的参照 ✅

**验证依据**:`backend/requirements` 锁定 `fastapi==0.111.1`、`celery==5.4.0`、`redis==4.5.1`、`SQLAlchemy==2.0.21`、`aiomysql`;`.env.example` 中 `CELERY_BROKER_URL=redis://...` 与 `CELERY_RESULT_BACKEND=redis://...`;`docker-compose.yml` 定义了 `app` / `celery-worker` / `celery-beat` 三个服务共用同一镜像,靠 `command:` 区分。README 自述栈为「python3 + fastApi + celery + sqlalchemy + redis」。

**值得抄的**:

- **三服务 compose 拆分**(app / worker / beat 共用一个镜像,不同 command)—— 这正是我们需要的部署形态
- `celery_worker/scheduler/` 是**数据库驱动的 beat 调度器**(含 models / session / crontab),这是 Celery beat 文件式调度在多副本部署下的标准修复方案。我们选了更简单的 tick 方案(见架构设计 D5),但它的实现可作为参考

**要避开的**:

- 只有 MySQL。换 PG 需要改 `asyncpg` + `postgresql+asyncpg://`
- `celery==5.4` 配同步 `pymysql` 做 beat 存储,而应用是异步 —— **两套 ORM 并存**。我们的 D6 决策(API 异步 / worker 同步)是有意为之的显式边界,不是这种无意的分裂

**另一个重要发现**:zerorunner 是 **HttpRunner v4 的改名 fork**(`zerorunner/testcase.py:ZeroRunner`),它没有用 pytest,而是自己写了 JSON DSL 解释器。数据模型上,`api_case_step` 是每步一行、带约 15 个 JSON 列;`api_case` 上有一句注释 `# todo ... 后面会拆为独立的表管理`;报告明细类名是动态生成的 `api_test_report_detail_{id % 1}`,也带「以后分片」的注释。**它自己知道当前设计有问题但没来得及改** —— 我们的 D7(版本化 JSON 文档 + 投影表)正是冲着这个问题去的。

### 4.2 pity — 最好的学习型代码库 ✅

**验证依据**:`requirements.txt` 含 `fastapi==0.75`、`sqlalchemy 1.4`、`redis==3.5.3`、**`APScheduler==3.8.0`(无 Celery)**,以及 `psycopg2-binary` + `asyncpg`(说明 PG 可配置);`ops/docker-compose.yaml` 为 mysql + redis + app;README 技术栈块列 FastAPI / SQLAlchemy / APScheduler / mitmproxy / Redis / Gunicorn / Nginx。前端是独立仓库 `wuranxu/pityWeb`(React 17 + Ant Design Pro)。685★,Apache-2.0,**最后推送 2024-05-29,已停更**,README 自述微服务化停滞。

**值得抄的**(尽管停更,代码结构仍然是最清晰的):

- `app/core/constructor/` 层:http / python / sql / redis 各类构造器
- `app/core/paramters/` 层:jsonpath / regex / kv / status-code 各类解析器
- **HAR 导入**(`har_convertor.py`)+ mitmproxy 录制 —— 「把真实流量变成测试用例」这条路径它走通了

这三块恰好对应我们引擎里最需要设计的部分(构造器 ≈ 步骤执行器,解析器 ≈ 提取器)。

**要避开的**:APScheduler 跑在 API 进程内,多副本时不像 Celery+Redis 那样能可靠协调 —— 我们选 Celery 是对的。依赖也严重过时(fastapi 0.75、pydantic 1.x)。

### 4.3 MeterSphere — 架构教科书,但代码不可复用 ✅

**验证依据**:13,579★,Java/Spring Boot 3.5,通过 `docker-compose.yml` 与 `pom.xml` 确认。GitHub 报告许可为 `NOASSERTION`(非标准许可,另有付费企业版)。

**关键修正**:v3 分支**已移除性能测试**模块,当前定位是「测试管理 + 接口测试」。网上大量介绍仍按旧版描述,需注意。

架构层面的可借鉴点(详见 [架构设计](架构设计.md) 各决策):

- 执行引擎是**自研 DSL 编译成 JMeter JMX**,而不是自己写 HTTP 客户端 —— 用 JMeter 的成熟能力换取引擎复杂度
- **资源池抽象**(`test_resource_pool` 分 NODE / K8S 两类 + `worker_node`),支持把执行节点部署到客户内网
- 分布式执行核心**不在本仓库**(外部制品 `ms-node-controller`),所以最关键的引擎实现读不到

**明确要避开的**:

- 148 张业务表**零外键**,引用完整性靠应用代码 + 定时清理任务兜底
- 版本管理用 `version_id` / `ref_id` / `latest` **行复制**,定义表随版本数乘法级膨胀
- 响应体存 `LONGBLOB` 内联,需要专门 sweeper 清理
- 测试计划报告与用例报告是**两套并行的表族**(`api_report*` 与 `api_scenario_report*`)

### 4.4 HttpRunner — DSL 设计最佳,但 v5 已转 Go ✅

**验证依据**:4,302★,当前主语言为 **Go**。三条产品线:v3(纯 Python + pytest)、v4(Go `hrp` + Python 双引擎)、v5(`master`,增加 UI/移动端/压测)。

**值得抄的**:

- **DSL 设计**:`config` + `teststeps` 的两段式结构,api 文件 / testcase 文件 / testsuite 三类文件的引用模型
- **变量解析**:`parse_variables_mapping()` 做固定点解析,并**显式检测自引用、未定义、循环引用**。我们的引擎照抄了这个思路(见执行引擎 §3)
- **报告体积卫生**:`shouldPrintBody()` 只输出 `text/*`、`application/json`、`application/xml`、form-urlencoded,其余打印 `(response body omitted for Content-Type: ...)`
- 4.x 引入 `pick_order`(sequential / random / unique)控制参数化取值顺序

**要注意的**:

- **v5 重写为 Go**,Python 版本停留在 v4。若考虑直接采用,需明确锁定 v4 而非跟随主线
- 4.x 里 Python 包**并不是 pytest 插件**(没有 `pytest11` 入口点),而是 **YAML → pytest 代码生成器 + 启动器** —— 它会往用户的源码树里写 `_test.py` 文件。「pytest 插件」是简称,不是字面事实。这在多租户平台里是很别扭的行为
- 提取只支持 **JMESPath + 正则**,没有 JSONPath。而 Postman 用户预期的是 JSONPath

### 4.5 RunnerGo — 实时控制做得最好,但已停更 ✅

**验证依据**:807★(GitHub)/ 826★(Gitee),Go 微服务拆成六个仓库,最后推送 **2024-07-09**。前端是 **React,不是 Vue3**。

**值得抄的**:

- **实时控制**:management 往 Redis 写停止标志,engine 订阅 pub/sub `SubscriptionStressPlanStatusChange:<reportId>`,支持运行中停止,甚至**运行中调整并发和时长**
- **每个执行独占一个 Kafka 分区**,实现执行间隔离
- 步骤树是**二维数组 `Scene.NodesRound [][]Event`**(外层轮次严格串行,轮次内节点并发),配合 `sync.Map` 记录前驱完成状态做 DAG 依赖 —— 这个模型比纯 JSON 树更容易做并发

**要避开的**:

- 同一个结构体在 ≥4 个包里手工镜像(`AssertionText` 同时存在于 engine、management 的 `dal/rao/*`、`dal/run_plan/plan.go` 和 Mongo 的 `mao`)
- `report_data` 是**一个 Mongo 文档装整个 JSON 字符串**
- 步骤模型不完整:无循环控制器、无事务控制器;**XPath 断言是空结构体未实现**;OSS 版 JS 脚本被注释掉
- 响应体存 Mongo,无 GridFS、无大小保护,报告「长跑冲突」

### 4.6 两个 FastAPI 小队项目 — 现代依赖集的样本 ✅

- **ntest**(107★,MIT,2026-10-14 推送):`fastapi==0.128.0`、`SQLAlchemy==2.0.45`、Tortoise、`asyncpg` + `psycopg2`、playwright、APScheduler。**无 redis、无 celery**。可以作为「2026 年一个 FastAPI 平台依赖清单该长什么样」的参考,还带一个 MCP server。
- **ApiPulse**(2★):唯一确认同时携带 `aiomysql` + **`asyncpg`** 的小型 FastAPI 项目,`httpx` + APScheduler。它的差异化前提是「把真实 HTTP 流量(HAR / mitmproxy)转成测试用例」—— 与 pity 的思路一致,值得作为产品方向参考。

> 注:两个 agent 分别报告 ntest 为 107★ 与 74★,系快照时间差,以较新的 107★ 为准。

## 5. 从同类项目提炼的技术模式

以下模式在多个项目中重复出现,已融入我们的设计。

| 模式 | 出处 | 我们的采纳 |
|---|---|---|
| Web 请求与执行解耦 | MeterSphere、RunnerGo、zerorunner、TestersStageV2 **全部如此** | ✅ Celery,见架构设计 §2 |
| 可执行用例 = 版本化 JSON 文档 | TestersStageV2(`t_scene.dsl` + `t_scene_version.dsl_snapshot`) | ✅ D7 |
| 大响应体移出 OLTP 库 | LMeterX → S3;ntest 压测报告 → MinIO;MeterSphere 附件 → MinIO | ✅ D4 |
| 变量固定点解析 + 循环引用检测 | HttpRunner `parse_variables_mapping()` | ✅ 执行引擎 §3 |
| 断言分类体系 | MeterSphere `MsAssertion`(状态码/响应头/响应体/响应时间/脚本/变量) | ✅ 执行引擎 §5 |
| 报告体积卫生(按 Content-Type 决定是否存 body) | HttpRunner `shouldPrintBody()` | ✅ 执行引擎 §11 |
| 独立执行队列 | TestersStageV2 `-Q execute` | ✅ 架构设计 §5 |
| 数据库驱动调度器 | zerorunner `celery_worker/scheduler/` | ✅ 但简化为 tick 方案(D5) |
| JS 脚本沙箱 | Hoppscotch `faraday-cage`(QuickJS/WASM) | ⏸ 未实现,见未决问题 |

**取消机制是共性缺陷**,单独列出:

| 项目 | 取消实现 | 问题 |
|---|---|---|
| zerorunner | **无**(零处 `revoke` / `abort`) | 完全缺失 |
| TestersStageV2 | **无**(状态枚举里根本没有 `cancelled`) | 完全缺失 |
| llm-test-platform | 写 `status=CANCELLED`,但 worker 继续跑并覆盖为 `COMPLETED` | 装饰性,反而产生错误状态 |
| ntest(API 测试) | 进程内 `set` + `threading.Lock`,每 0.2s 轮询 | 仅在单进程单 worker 下正确,**加 worker 或多开 uvicorn 即静默失效** |
| ntest(压测) | 先写 DB `status=4` **再**读 PID 杀进程 | ✅ 唯一做对的:先落状态再动手 |
| LMeterX | 两阶段:`cancelled`(未认领)/ `stopping` → 引擎确认 → `stopped` | ✅ 状态机正确 |

ntest 的 API 测试实现是最有价值的反面教材 —— 它**看起来完全正确**,代码也清晰,但一旦部署形态变化就静默失效,而且失效方式是「取消按钮没反应」,没有任何报错。我们的 D3 就是针对这个设计的。

## 6. 差异化定位

调研显示的市场空白:

1. **技术栈空白**:FastAPI + Celery + PostgreSQL 的组合没有先例。这不是风险,是差异点 —— PG 在 JSONB、分区、`LISTEN/NOTIFY` 上的能力对这类平台是实质优势,而同类项目大多被 MySQL 的选择限制了(JSONB 索引、声明式分区都是 PG 独有或更成熟)。
2. **取消机制**:多数项目做错或没做。做对是可感知的产品优势。
3. **报告体量控制**:同类项目普遍在「报告把库撑爆」上踩坑,我们的 D4 从第一天就分流。
4. **不要追 AI 功能**:MeterSphere、BrickCoreTest、AngusTester 都在往 AI 助手上卷。这是当前的军备竞赛点,但不是基础能力的替代品 —— 执行引擎、取消、报告这些地基没打好,加 AI 只是让错误更快地产生。

## 7. 未能验证的事项

诚实列出,这些结论在后续引用时需重新核实:

- **MeterSphere**:`io.metersphere.engine.EngineFactory` / `MsHttpClient` 的内部实现,以及外部制品 `ms-node-controller` —— 均不在仓库内,无法阅读;`CompressUtils` 是否作用于报告体未确认;运行时实际使用的 Kafka topic 名(config 常量与旧文档不一致)
- **HttpRunner**:是否真正支持 pytest-xdist(该参数是不透明透传);v5 的 `hrp server` / `mcphost` 细节
- **RunnerGo**:OSS 版是否用到 ES;分页字段的确切名称;默认 Kafka topic 字符串(配置之间不一致,`report` 与 `runnergo` 都有)
