# 文档索引

接口自动化测试平台的全部项目文档。**新增文档一律写入 `docs/` 下对应类型的子目录**,不散落在仓库其他位置。

## 目录约定

| 目录 | 放什么 | 不放什么 |
|---|---|---|
| `research/` | 外部调研、竞品分析、技术选型的前期论证 | 我们自己的设计决策 |
| `design/` | 架构、数据模型、模块设计等设计文档 | 使用说明 |
| `api/` | 对外 API 的补充说明(OpenAPI 文档由服务自动生成,这里只放约定与示例) | 自动生成的产物 |
| `ops/` | 部署、运维、监控、故障处理 | 开发文档 |
| `adr/` | 架构决策记录。**重大决策的最终定论**,与 `design/` 里的论证过程互补 | 详细设计 |
| `guide/` | 面向使用者的操作指南 | 内部实现 |

按类型分目录,不按时间或作者分。一个文档属于哪一类,决定了它放在哪里。

## 建议阅读顺序

**新加入项目的人**:[架构设计](design/架构设计.md) → [执行引擎](design/执行引擎.md) → [数据模型](design/数据模型.md)

先理解「系统由哪些进程组成、执行是怎么发生的」,再看「数据长什么样」。反过来读会陷入表结构的细节,不容易建立整体图景。

**只想了解技术选型为什么这么做**:[同类项目调研](research/同类项目调研.md) → [架构设计 §4 关键决策](design/架构设计.md)

调研文档里有同类项目的踩坑记录,是各项决策的直接依据。

**要动手写代码**:[架构设计 §8 目录结构](design/架构设计.md) → [执行引擎 §1 边界与依赖注入](design/执行引擎.md)

## 维护约定

- **决策要记录被否决的方案**。只写「我们选了 X」的文档,三个月后没人知道为什么不能选 Y,于是会有人重新提一遍 Y。每项关键决策都应包含:选了什么、否决了什么、为什么。
- **数据来源要标注**。调研文档里区分「已验证」与「未验证」,设计文档里标注决策依据的出处。二手结论不标注来源,后续会被当作事实引用。
- **未决问题单列章节**。设计文档末尾的「未决问题」是有意保留的 —— 假装所有问题都已解决,会让读者在遇到时才发现在文档里找不到答案。
- **文档与代码同仓库、同 PR**。接口变了、表结构变了,对应的设计文档在同一个 PR 里更新。
