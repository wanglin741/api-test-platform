# 执行引擎

> `app/engine/` · 纯逻辑库,不依赖 FastAPI / Celery / ORM

## 1. 边界与依赖注入

引擎是**一个可独立单测的库**,不是应用的一部分。硬约束:

```
engine/ 可以 import: 标准库、httpx、pydantic、jsonpath、croniter(仅解析)
engine/ 禁止 import: fastapi, celery, sqlalchemy, app.models, app.services
```

理由:引擎是全平台最需要测试覆盖的部分。一旦它能 import FastAPI,测试就得起 ASGI 应用;一旦能 import Celery,测试就得起 broker;一旦能 import ORM,测试就得起数据库。守住这条线,引擎的测试就是纯内存的,毫秒级。

引擎与外界的三处交互通过**协议(Protocol)注入**:

| 协议 | 职责 | 生产实现 | 测试实现 |
|---|---|---|---|
| `ResultSink` | 步骤结果落库 | `DbResultSink` | `InMemorySink` |
| `ProgressPublisher` | 进度事件推送 | `RedisStreamPublisher` | `NullPublisher` |
| `CancellationToken` | 查询是否已请求取消 | `RedisCancellationToken` | `NeverCancelled` / `ImmediateCancel` |

用 `typing.Protocol` 定义,不引入抽象基类。CI 里用 `import-linter` 的 `forbidden` 契约守住边界。

## 2. 用例 DSL

可执行用例是一份 JSON 文档,对应 `test_case_version.dsl`。

```json
{
  "dsl_version": 1,
  "config": {
    "variables": { "base_url": "https://api.example.com" },
    "parameters": {
      "username": ["alice", "bob"],
      "password": "secret"
    },
    "parameters_setting": { "pick_order": "sequential" },
    "timeout_ms": 10000,
    "fail_fast": false,
    "max_duration_ms": 600000
  },
  "steps": [
    {
      "id": "s1",
      "name": "登录",
      "type": "http",
      "enabled": true,
      "request": {
        "method": "POST",
        "url": "{{base_url}}/login",
        "headers": { "Content-Type": "application/json" },
        "body": { "type": "json", "content": "{\"user\": \"{{username}}\"}" },
        "auth": { "type": "inherit" },
        "timeout_ms": 5000,
        "follow_redirects": true,
        "verify_ssl": true
      },
      "extract": [
        { "name": "token", "type": "jsonpath", "expression": "$.data.token", "scope": "case" }
      ],
      "assert": [
        { "type": "status_code", "operator": "eq", "expected": 200 },
        { "type": "jsonpath", "expression": "$.code", "operator": "eq", "expected": 0,
          "message": "业务码应为 0" }
      ],
      "retry": { "times": 2, "interval_ms": 1000, "on": ["error"] }
    }
  ]
}
```

**`dsl_version` 是必填字段**。它是引擎的演进契约:未来 DSL 结构变化时,引擎可以按版本分派解析逻辑,而不是让老用例静默跑错。没有这个字段,任何格式调整都会变成一次全量数据迁移。

### 步骤类型

| `type` | 作用 | 子步骤 |
|---|---|---|
| `http` | 发一个 HTTP 请求 | — |
| `wait` | 等待固定时长 | — |
| `if` | 条件分支 | `then` / `else` |
| `loop` | 遍历数组或固定次数 | `steps` |
| `case_ref` | 嵌套调用其他用例 | — |

**`case_ref` 是刻意保留的**:复杂场景需要复用「登录」这类公共前置步骤。但嵌套会让变量作用域和失败定位变复杂,因此限制**最大嵌套深度为 3**,超出则保存时报错。没有这个上限,一个循环引用的用例集合会让引擎无限递归。

**暂不支持的步骤类型**:脚本步骤(`script`)、数据库步骤、WebSocket 步骤。它们各自需要独立的沙箱或连接管理,见 [架构设计 §10 未决问题](架构设计.md)。

## 3. 变量系统

### 语法

`{{variable_name}}`。选这个语法是因为它与 Postman 一致,而 Postman 是最可能的用例导入来源。

转义:`\{{literal}}` 输出字面量 `{{literal}}`。

内置函数(不带用户定义变量):

| 函数 | 说明 |
|---|---|
| `{{$uuid}}` | 随机 UUID4 |
| `{{$timestamp}}` | 当前 Unix 秒 |
| `{{$timestamp_ms}}` | 当前 Unix 毫秒 |
| `{{$randomInt}}` | 0~1000000 随机整数 |
| `{{$randomString(n)}}` | 长度 n 的随机串 |
| `{{$env.NAME}}` | 进程环境变量(**仅白名单前缀**,见下) |

`$env.` 必须限制在白名单前缀内(如 `TEST_`)。否则用例作者可以读到 `DATABASE_URL`、`ANTHROPIC_AUTH_TOKEN` 这类平台自身的凭据,并让它们出现在请求头或报告里。这是一个真实的凭据泄漏路径。

### 作用域与优先级

从低到高,后写的覆盖先写的:

| 层级 | 来源 | 生命周期 |
|---|---|---|
| 1 | 内置函数 | 求值时 |
| 2 | 项目级变量 | 整个执行 |
| 3 | 环境级变量 | 整个执行 |
| 4 | 用例 `config.variables` | 单次用例执行 |
| 5 | 数据驱动当前行 `parameters` | 单次迭代 |
| 6 | 步骤级 `variables` | 单步 |
| 7 | 运行时提取(`scope: case`) | 提取后至用例结束 |
| 8 | 嵌套用例 `export` 回传 | 调用点之后 |

### 解析规则

**固定点解析**:反复替换直到没有 `{{}}` 为止,**最大 5 轮**。变量值本身可以引用其他变量(`{{host}}` → `{{base_url}}/v1` → `https://...`),固定点解析支持这种链式引用。5 轮上限是防死循环的兜底。

**循环引用必须显式检测**,而不是靠轮数上限兜底。解析时维护一条引用链,若当前变量已在链上,立即报错并输出完整链:

```
循环引用: a -> b -> c -> a
```

靠轮数上限兜底的问题是错误信息会变成「解析超过 5 轮」,用户完全不知道是哪个变量绕回来了。HttpRunner 的 `parse_variables_mapping()` 就显式做了自引用、未定义和循环引用的检测,值得照抄。

**未定义变量 → 步骤 `skipped`,不是 `failed`**。

这条规则是刻意设计的。考虑这个序列:步骤 1 断言失败 → 没有提取出 `token` → 步骤 2 的请求 URL 里含 `{{token}}`。如果未定义变量算 `failed`,报告里会出现两条失败,其中一条是假的。真实原因只有一个:步骤 1 挂了。

所以:请求构建阶段遇到未定义变量 → 该步骤 `skipped`,`error_message` 写明缺失的变量名。断言失败引起的连锁反应不会污染报告。

`skipped` 的步骤不参与通过率计算,但要在报告里显著标出 —— 用户需要知道「这条用例其实没跑完」。

**非字符串类型的变量**:JSON body 里 `{"id": "{{user_id}}"` 若 `user_id` 是数字,替换后得到字符串 `"123"` 而非 `123`。

处理方式:提供 `{{user_id:int}}` 这类类型强制转换语法,或在 JSON body 场景下做类型推断 —— 当整个字符串值恰好是单个 `{{var}}` 占位符且变量是数字/布尔时,替换为原生类型。

采用**后者**(整体占位符才推断类型),因为 `"prefix-{{id}}"` 这种拼接场景本就该是字符串。这个规则必须写进用户文档,否则是最常见的困惑点。

## 4. 提取器

`extract` 数组在响应返回后、断言执行前运行。提取结果注入变量作用域。

| `type` | 参数 | 说明 |
|---|---|---|
| `jsonpath` | `expression` | 默认。`$.data.token`、`$.items[0].id` |
| `regex` | `expression`, `group` | 正则捕获组,默认第 1 组 |
| `header` | `name` | 响应头,大小写不敏感 |
| `cookie` | `name` | |
| `status_code` | — | |
| `body` | — | 整个响应体为字符串 |

**提取失败的处理**:分两种。

- `required: true`(默认)—— 提取不到则步骤 `failed`,错误信息含表达式和响应体片段
- `required: false` —— 提取不到则变量不注入,后续引用它的步骤会 `skipped`

默认严格是刻意的。静默的 `null` 会一路传到断言阶段,报出「期望 200 实际 null」这种误导性信息。

**`scope` 字段**:

- `case`(默认)—— 变量在本用例内可见
- `environment` —— 写回环境变量。**需要显式授权**,见下

`environment` 作用域会让一次执行的副作用影响后续所有执行,在多用户场景下是共享可变状态。默认关闭,由项目设置里的开关控制;开启时写入 `audit_log`。

**JSONPath 性能**:`jsonpath-ng` 是纯 Python 实现,在长跑中会成为瓶颈。响应体先用 `orjson` 解析(比标准库快数倍),再交给 JSONPath。若仍不够,对同一表达式的重复求值做编译缓存。这是后续优化点,不在首版。

## 5. 断言体系

### 断言类型

| `type` | 取值来源 |
|---|---|
| `status_code` | 响应状态码 |
| `jsonpath` | 响应体按 JSONPath 取值 |
| `header` | 响应头 |
| `response_time_ms` | 客户端测得的总耗时 |
| `body_contains` | 响应体子串 |
| `body_regex` | 响应体正则 |
| `json_schema` | 响应体结构校验(JSON Schema) |
| `variable` | 变量值 |
| `script` | JS 沙箱(未实现) |

### 操作符

`eq` · `ne` · `gt` · `gte` · `lt` · `lte` · `contains` · `not_contains` · `startswith` · `endswith` · `regex_match` · `in` · `not_in` · `is_null` · `not_null` · `length_eq` · `type_match`

`in` / `not_in` 的 `expected` 是数组。`length_eq` 对字符串取长度、对数组取元素数。

**类型比较要宽容但不能太宽容**:`"200"` 与 `200` 判等。

实现:先尝试数值比较(两侧都能转成数字时),否则字符串比较。**不**做 `true`/`"true"` 这种跨类型宽松比较 —— 那会让 `{"deleted": true}` 断言 `"1"` 也通过。具体规则:`str == str`、`num == num`、`bool == bool`,数字与数字字符串互通,其余一律不等。

### 断言失败的语义

**单步内所有断言全部执行**,不做短路。一次跑出该步骤的全部问题,而不是修一个跑一次。

**`response_time_ms` 的测量口径必须说清楚**。用 `time.perf_counter()` 包住整个 `await`,它包含 DNS 解析、TCP 连接、TLS 握手和**连接池排队等待**。

连接池排队时间尤其要警惕:若 `max_connections` 小于并发数,请求会在池里排队,这段时间被计入「响应时间」,报告里会出现莫名其妙的慢。**因此 `max_connections` 必须 ≥ 环境配置的并发数**,引擎启动时校验这个不变量,不满足直接报错,而不是让用户对着假数据排查。

`httpx.Response.elapsed` 也可用,但它要求在读取响应体之后才能访问(否则抛 `RuntimeError`),且同样包含连接建立耗时。首版用 `perf_counter` 手动测量,口径明确可控。

## 6. 步骤编排

### 顺序执行

单用例内步骤**严格顺序**。不做步骤级并行,因为步骤之间存在变量依赖(步骤 N 的提取供步骤 N+1 使用),静态分析依赖关系得不偿失。

### `if` 条件

`condition` 是一个表达式字符串,求值为布尔。支持:

```
{{token}} != ''
{{status}} == 200
{{count}} > 5
{{name}} in ['a', 'b']
```

**不引入完整的表达式语言**。支持 `== != > >= < <= in not_in` 和 `and` / `or` / `not`,用 Python 的 `ast` 模块解析后**白名单求值** —— 绝不用 `eval()`。表达式语言的复杂度必须止步于此;需要更复杂的逻辑时,正确的做法是把判断前移到一个接口调用或后端字段上,而不是在测试平台里写脚本。

### `loop` 循环

```json
{
  "type": "loop",
  "items": "$.data.list",
  "item_var": "item",
  "index_var": "idx",
  "max_iterations": 100,
  "steps": [ ... ]
}
```

- `items` 是 JSONPath 表达式(对**变量作用域内的对象**求值,通常是上一步提取的变量)或整数(固定次数)
- `max_iterations` **必填且强制**。没有上限的循环在 `items` 意外返回大数组时会跑飞,消耗掉整个执行时间预算
- 循环体内每次迭代注入 `item_var` 和 `index_var`

### `case_ref` 嵌套调用

```json
{ "type": "case_ref", "case_id": 123, "version": 3, "export": ["token"] }
```

被调用的用例在**新的变量作用域**中执行(继承调用者的作用域为父作用域),执行完毕后 `export` 列出的变量回传到调用者作用域。

**版本必须显式锁定**。不写 `version` 则取该用例的最新版本 —— 但这样「引用了哪个版本」就不可重现了。默认取最新,同时在保存用例时把解析出的版本号写进 DSL,后续手动更新。

## 7. 数据驱动

```json
"parameters": {
  "username": ["alice", "bob"],
  "password": "secret"
}
```

- 数组值 → 每个元素一轮,产生 2 轮迭代
- 标量值 → 每轮都是同一个值

**多变量时的组合方式**:`username` 有 2 个值、`password` 有 3 个值时,是笛卡尔积(6 轮)还是按位配对(2 轮,取最短)?

**默认笛卡尔积**,但提供 `parameters_setting.strategy`:

| `strategy` | 行为 |
|---|---|
| `cartesian`(默认) | 笛卡尔积 |
| `zip` | 按位配对,以最短的为准 |
| `sequential` | 同上,语义更明确的别名 |

选笛卡尔积作默认是因为它最不容易静默丢数据 —— `zip` 在数组长度不等时会悄悄截断,用户很难察觉自己有 3 个密码只跑了 2 个。

`parameters_setting.pick_order` 控制顺序: `sequential`(默认)/ `random` / `unique`。

**每轮迭代是一次独立的用例执行**,产生一组完整的步骤结果,`run_step_result.parent_index` 或迭代序号列标识归属。报告中按迭代分组展示。

## 8. 并发模型

### 层次

| 层次 | 是否并行 | 机制 |
|---|---|---|
| 计划内多个用例 | 取决于 `plan.execute_mode` | `asyncio.gather` + `Semaphore(plan.concurrency)` |
| 单个用例内步骤 | **严格串行** | — |
| 数据驱动迭代 | **严格串行** | 迭代间可能共享变量 |
| 单个请求内部 | — | httpx 连接复用 |

### 计划级并行为什么不用 Celery canvas

直觉上「计划内 N 个用例并行」应该用 Celery 的 `group` + `chord`。**这条路被 D1 堵死了**:chord 需要一个可用的结果后端(否则报 `E_CHORD_NO_BACKEND`),而我们的执行任务 `task_ignore_result = True`。

三个选项:

1. 为 chord 单独开启结果后端 —— 与 D1 冲突,且把结果又写回了 Redis
2. 用「父任务派发子任务 + Redis 计数器做 join」自建 fan-out/fan-in —— 可行但要自己处理子任务失败、超时、worker 丢失,复杂度不低
3. **在单个 Celery 任务内用 `asyncio.gather` 并行** ← 采用

选 3 的理由:一次计划内的用例数通常在几十到几百,单个 worker 进程的 asyncio 完全能承载(纯 I/O 等待,不占 CPU)。它不需要结果后端,不需要跨进程协调,失败和取消的语义都在一个进程内,简单得多。

**代价要说清楚**:单次计划受限于单 worker 的处理能力,不能跨 worker 水平扩展。若日后需要跑上千用例的计划,再引入选项 2。首版不为一个尚未出现的需求买单。

### 并发上限的校验

启动一次执行前校验三个数,不满足则拒绝执行并给出明确错误:

```
plan.concurrency ≤ environment.max_concurrency
environment.max_concurrency ≤ httpx.Limits.max_connections
```

第三个约束就是 §5 提到的连接池排队问题。这三个数分散在计划配置、环境配置和引擎常量里,很容易配出「并发 200 但连接池 100」这种组合 —— 结果是报告里一半请求的响应时间被池等待污染。**校验前置**,不要等到用户发现数据不可信。

## 9. 超时、重试与错误分类

### 超时层次

| 层次 | 默认 | 说明 |
|---|---|---|
| 连接 | 5s | `httpx.Timeout(connect=)` |
| 读取 | 10s | |
| 连接池 | 5s | 获取连接的等待上限 |
| 单步骤 | 继承用例 `timeout_ms` | 可被步骤覆盖 |
| 单次执行(软) | 55 min | `task_soft_time_limit`,可捕获做清理 |
| 单次执行(硬) | 60 min | `task_time_limit`,杀进程 |
| 用例总时长 | `config.max_duration_ms` | 引擎内部检查,超时则优雅停止 |

`max_duration_ms` 是引擎自己实现的,与 Celery 的时限不同 —— 它作用于**单个用例**,在用例级并行时,一个卡死的用例不会拖垮整个计划的其他用例。

### 错误分类

| 类别 | 触发 | 默认重试 |
|---|---|---|
| `error` | 网络异常、超时、连接拒绝、DNS 失败 | **是** |
| `failed` | 断言不通过 | **否** |
| `skipped` | 未定义变量、`enabled: false`、取消 | 否 |

**断言失败默认不重试**是刻意的。断言失败是一个确定的业务结果 —— 接口返回了错误的数据,再请求一次不会变对。把断言失败也纳入重试会掩盖真实的间歇性缺陷,并让执行时间翻倍。

只有网络层的 `error` 才重试,因为那可能是瞬时的。

重试配置:

```json
{ "times": 2, "interval_ms": 1000, "on": ["error"], "backoff": "exponential" }
```

重试时**必须重新求值变量** —— 上一次重试可能更新了某个变量。直接复用已构建好的请求对象会跳过这一步。

## 10. 取消的协作点

`CancellationToken` 在以下位置被检查:

1. 每个步骤开始前
2. 每次重试前
3. 循环每次迭代前
4. 数据驱动每行迭代前
5. `wait` 步骤的等待期间
6. 嵌套用例调用前

第 5 点容易漏:`wait` 步骤如果直接 `asyncio.sleep(30)`,这 30 秒里取消不会生效。实现为**分段 sleep**,每 0.2s 检查一次 token。

**Token 的实现带本地缓存**:不查 Redis 那么频繁。缓存 0.2s,即最坏情况下取消延迟 0.2s,可接受,而 Redis 的 QPS 降低一个数量级。

**取消后的结果处理**:已完成的步骤结果保留,未开始的标记 `skipped`,正在执行的请求**不强制中断** —— 让它自然结束(通常是几百毫秒),然后停止。强制取消会得到一堆没有响应的结果行,不如让在途请求收尾。

## 11. 结果采集

### 响应体截断在引擎层完成

**这是硬要求**。一个返回 500 MB 的接口,如果先把响应读进内存再判断大小,worker 直接 OOM。

实现:用 `httpx` 的流式读取,累计字节数超过 `body_max_bytes`(项目设置,默认 64 KB)即停止读取并关闭连接,标记 `truncated: true`。

`httpx` 默认的 `client.request()` 会把整个响应体读进内存。必须显式用 `client.stream()` 并配合 `aiter_bytes()`,自己累加并截断。

代价是截断后无法做基于完整响应体的断言(`body_contains` 若目标在截断点之后会失败)。**因此截断阈值必须与断言需求协调** —— 若某步骤有 `body_contains` 断言,阈值应放宽或该步骤关闭截断。这个规则要在文档里写明,否则用户会遇到「明明返回里有这个字符串,断言却失败」的诡异现象。

### 写入时机

**每步完成立即写 PG**,不批量缓冲。

理由:用户要实时看到进度。批量缓冲(比如攒 10 步写一次)会让报告出现「卡住不动然后突然跳 10 步」的观感。单次执行上千次 INSERT 对 PG 不是压力,瓶颈从来不在 INSERT。

进度事件另外推 Redis Stream,**限流至 1 秒一次**。

### 大响应体转对象存储

引擎不直接写 MinIO。引擎产出结果对象,由 `ResultSink` 实现决定:≤ 阈值内联写 `response_body`,`> 阈值` 上传 MinIO 后写 `response_body_object_key`。

把存储决策放在 Sink 而非引擎,是为了让引擎的单元测试不需要 MinIO。

## 12. 测试策略

引擎的测试不需要任何外部依赖,这是 §1 边界约束换来的收益。

| 层次 | 手段 |
|---|---|
| 变量解析 | 表驱动:输入 DSL 片段 + 作用域,断言解析结果。**重点覆盖**循环引用、未定义、链式引用、类型推断 |
| 提取器 | 固定响应体 + 表达式,断言提取值。覆盖路径不存在、类型不匹配 |
| 断言求值 | 每个操作符 × 每种类别的组合矩阵,重点覆盖类型宽容规则 |
| 步骤编排 | `httpx.MockTransport` 伪造响应,断言步骤执行顺序与状态 |
| 取消 | `ImmediateCancel` token,断言执行在正确的协作点停止 |
| 超时/重试 | MockTransport 注入延迟和异常,断言重试次数与分类 |
| 端到端 | 起一个真实的 FastAPI 测试服务,跑完整 DSL |

`httpx.MockTransport` 是关键 —— 它让 HTTP 层的所有分支(超时、连接错误、各种状态码、超大响应)都能在毫秒级测到,不用起真实服务。

## 13. 与任务层的关系

`app/tasks/engine_tasks.py` 的职责仅限于:

```
1. 加载 run / case_version / environment / plan 配置 (同步 Session)
2. 组装 EngineContext(变量、环境、取消 token、Sink)
3. asyncio.run(engine.execute(dsl, context))
4. 汇总结果,写 run.summary 与终态
```

**任务层不含任何业务规则**。所有判断(变量怎么解析、断言怎么算、什么时候取消)都在引擎里。任务层是胶水,它唯一的复杂性来自同步/异步边界和所有权校验。

任务入口的第一件事是**幂等检查**:若 `run.status` 已是终态,直接返回。这是 `acks_late` + `task_reject_on_worker_lost` 带来的必然要求 —— worker 崩溃后任务会被重投。
