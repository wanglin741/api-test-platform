# 数据模型

> 数据库:PostgreSQL 18 · ORM:SQLAlchemy 2.0 · 迁移:Alembic

## 1. 总体约定

**主键**:全表使用 `BIGINT` 自增还是 `UUID`?

- 业务实体用 `BIGINT` 自增(项目、用例、环境等)。索引更小,自增插入无页分裂,URL 可读。
- **`run` 和对外暴露的 token 用 `UUID`**。执行 ID 会被写进 SSE 频道名、Redis key、CI 回调 URL,用自增 ID 会泄漏业务量且容易被枚举。

**软删除**:`deleted_at TIMESTAMPTZ NULL`,所有查询默认带 `WHERE deleted_at IS NULL`。用一个 SQLAlchemy 的 `SoftDeleteMixin` 统一实现,不要靠每个 service 手写条件 —— 漏一处就是数据泄漏。

**外键**:**全部显式建 FK 约束**。

这一条是刻意与 MeterSphere 相反的。MeterSphere 148 张业务表**零外键**,靠应用代码 + 定时清理任务维持引用完整性。代价是孤儿行只能靠 sweeper 兜底,而且任何一处删除逻辑写漏就会留下悬挂引用。我们接受 FK 带来的少量写入开销和删除顺序约束,换数据库层面的正确性。

例外:对**极高写入量**的 `run_step_result` / `mock_request_log`,其 `run_id` / `rule_id` 外键保留,但**不用 `ON DELETE CASCADE`**,改用分区表的 `DROP PARTITION` 做批量清理 —— 级联删除百万行会长时间持锁。

**时间**:统一 `TIMESTAMPTZ`,`created_at` / `updated_at` 由数据库默认值生成,不信任应用时钟。

**命名**:Alembic 必须配置 `MetaData` 的 naming convention,否则自动生成的约束名不稳定,后续 `ALTER` / `downgrade` 会出错。

```python
NAMING_CONVENTION = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

**枚举**:用 PG 原生 `ENUM` 还是 `VARCHAR` + CHECK?

用 `VARCHAR` + CHECK 约束。PG 原生 enum 增加取值要 `ALTER TYPE ... ADD VALUE`,且在事务里有额外限制,迁移体验很差。状态机字段改动频繁,不值得。


### `project_member`

| 列 | 类型 | 说明 |
|---|---|---|
| project_id | BIGINT FK→project | PK 组成部分 |

## 4. 目录树

### `folder`

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| project_id | BIGINT FK→project | |
| scope | VARCHAR(16) | `api` / `case` / `scene` / `mock` |
| parent_id | BIGINT FK→folder NULL | 自引用,`ON DELETE CASCADE` |
| name | VARCHAR(128) | |
| sort_order | INT | 同级排序 |

UNIQUE `(project_id, scope, parent_id, name)`。

一张表承载四种实体的目录。这与 RunnerGo 的 `target` 表把五种**实体**混在一张表不同 —— 目录(folder)在四种场景下语义完全一致,只是树的所有者不同,用 `scope` 区分是合理的。而实体本身(接口定义、用例、场景)语义差异大,必须分表。

**排序用整数 `sort_order` 有并发问题**:两个用户同时拖拽会导致重排丢失。当前实现接受这个风险(低频操作,冲突可感知);若成为问题,改用小数排序键或 `FOR UPDATE` 锁同级兄弟节点。

| 列 | 类型 | 说明 |
|---|---|---|

### `api_definition_version`

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| api_definition_id | BIGINT FK→api_definition | |
| version | INT | |
| request | JSONB | 完整请求定义 |
| response_schema | JSONB | 期望响应结构,用于「结构断言」与 Mock 生成 |
| change_note | VARCHAR(255) | |
| created_by / created_at | | |

UNIQUE `(api_definition_id, version)`。

**版本是快照表,不是行复制**。每次「发布」写一条不可变快照,`api_definition` 本体只保留当前态。对比 MeterSphere 的 `version_id` / `ref_id` / `latest` 三列行复制方案 —— 那个方案让定义表随版本数乘法级膨胀,且「查最新版」需要 `latest = 1` 这种易错的查询条件。

`request` 的 JSONB 结构:

```json
{
  "headers": {"Content-Type": "application/json"},
  "query": [{"name": "page", "value": "1", "enabled": true}],
  "path_params": {},
  "body": {"type": "json", "content": "{\"name\": \"{{name}}\"}"},
  "auth": {"type": "inherit"},
  "timeout": 10,
  "follow_redirects": true,
  "verify_ssl": true
}
```

`body.type` ∈ `json` / `raw` / `form-data` / `x-www-form-urlencoded` / `binary` / `none`。

### `test_case_version`

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| test_case_id | BIGINT FK→test_case | |
| version | INT | |
| dsl | JSONB | **可执行文档,执行的唯一事实来源** |
| change_note | VARCHAR(255) | |
| created_by / created_at | | |

UNIQUE `(test_case_id, version)`。

**为什么是 JSON 文档**:整份用例能一次性下发给 worker,不必在 worker 侧做多表 join 拼装;版本快照就是复制一个 JSONB 值;diff 两个版本是 JSON diff。DSL 的详细结构见 [执行引擎](执行引擎.md)。

**执行时锁定版本**:`run` 记录 `case_version`,这样「改了用例之后看旧报告」仍然能还原当时跑的是什么。

### `test_case_step`

**投影表**,从 `dsl` 派生,用于回答「这个接口定义被哪些用例引用」这类反向查询。

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| test_case_id | BIGINT FK→test_case | |
| version | INT | |
| step_index | INT | |
| name | VARCHAR(128) | |
| step_type | VARCHAR(32) | `http` / `wait` / `script` / `if` / `loop` / `case_ref` |
| ref_api_id | BIGINT FK→api_definition NULL | |
| ref_case_id | BIGINT FK→test_case NULL | 嵌套调用其他用例 |

UNIQUE `(test_case_id, version, step_index)`。

**这张表是可重建的**。任何时候都可以从 `dsl` 重算,所以它损坏或过时不是数据丢失。在用例保存的同一事务里重写该版本的投影行。

MeterSphere 用 `resource_id` 一个多态列 + `step_type` 判别指向三种实体,那样数据库无法校验引用有效性。这里拆成两个带真实外键的可空列,引用完整性交给数据库。

## 9. 执行与结果

### `run`

| 列 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | 对外暴露,写进 SSE 频道与 CI 回调 |
| project_id | BIGINT FK→project | |
| plan_id | BIGINT FK→test_plan NULL | |
| schedule_id | BIGINT FK→schedule NULL | 定时触发时记录来源 |
| case_id | BIGINT FK→test_case NULL | 单用例调试执行 |
| case_version | INT | 锁定的用例版本 |
| environment_id | BIGINT FK→environment | |
| trigger_mode | VARCHAR(16) | `manual` / `schedule` / `openapi` / `ci` |
| triggered_by | BIGINT FK→user NULL | 定时/CI 触发时为空 |
| status | VARCHAR(16) | 见下方状态机 |
| celery_task_id | VARCHAR(64) | |
| worker_id | VARCHAR(64) | **所有权令牌**,见下 |
| cancel_requested_at | TIMESTAMPTZ NULL | |
| started_at / finished_at | TIMESTAMPTZ | |
| duration_ms | INT | |
| summary | JSONB | 见下 |
| created_at | TIMESTAMPTZ | |

索引:`(project_id, created_at DESC)`、`(status)`、`(plan_id, created_at DESC)`、`(celery_task_id)`。

**状态机**:

```
pending ──▶ running ──┬──▶ success
   │           │      ├──▶ failed      (断言失败)
   │           │      └──▶ error       (引擎/网络异常)
   │           ▼
   │       stopping ──▶ stopped
   └──────────────────▶ stopped         (排队中被取消)
```

`stopping` 是独立状态,不能省。从发出取消到 worker 真正停下之间有窗口,直接置 `stopped` 会让 UI 显示「已停止」而实际还在发请求。

**`worker_id` 所有权令牌**:worker 认领任务时写入自己的 ID(进程启动时生成的 UUID + 主机名),每次写结果前校验 `run.worker_id == self.worker_id`,不匹配则放弃写入。

这是防「僵尸 worker 覆盖结果」的:worker 被 `task_time_limit` 硬杀后任务被重投,新 worker 接手;此时旧进程若尚未完全退出并写回终态,会覆盖掉新结果。同类项目 `llm-test-platform` 就有这个 bug —— 取消任务后 worker 继续跑,最后把 `CANCELLED` 覆盖成 `COMPLETED`。

**`summary` 结构**:

```json
{
  "total": 42, "passed": 40, "failed": 1, "error": 1, "skipped": 0,
  "assertion_total": 180, "assertion_passed": 176,
  "request_duration_ms": 15230,
  "pass_rate": 0.952
}
```

**计划执行**(run.plan_id 非空)时追加 `cases` 用例级结果数组 —— 字段形状与汇总一致,另附归属;被跳过的用例没有步骤行,不在此记下就「凭空消失」:

```json
"cases": [
  { "case_index": 0, "case_id": 11, "case_name": "登录", "status": "success",
    "total": 2, "passed": 2, "failed": 0, "error": 0, "skipped": 0 },
  { "case_index": 1, "case_id": 12, "case_name": "下单", "status": "skipped",
    "total": 0, "passed": 0, "failed": 0, "error": 0, "skipped": 0 }
]
```

反范式存在 `run` 上,避免列表页为了显示通过率去聚合 `run_step_result`。

### `run_step_result`

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| run_id | UUID FK→run | |
| step_index | INT | |
| step_name | VARCHAR(255) | |
| step_type | VARCHAR(32) | |
| parent_index | INT NULL | 循环/条件体内步骤的父步骤序号 |
| case_index | INT | 用例归属序号:计划执行时 = 清单位置;单用例执行恒 0 |
| case_id | BIGINT NULL | **冗余副本,不设外键** —— 用例删除后历史报告仍可还原归属 |
| status | VARCHAR(16) | `passed` / `failed` / `error` / `skipped` |
| duration_ms | INT | |
| request_method / request_url | VARCHAR | |
| request_headers | JSONB | 已脱敏 |
| request_body | TEXT | 截断 |
| response_status | INT | |
| response_headers | JSONB | |
| response_size | INT | |
| response_body | BYTEA NULL | **≤ 64 KB 时内联** |
| response_body_object_key | VARCHAR(512) NULL | **> 64 KB 时指向 MinIO** |
| response_body_sha256 | CHAR(64) NULL | |
| response_body_truncated | BOOL | |
| extracted_variables | JSONB | 该步提取出的变量 |
| assertions | JSONB | 断言结果数组 |
| assertion_total / assertion_passed | INT | 反范式计数 |
| error_message | TEXT | |
| created_at | TIMESTAMPTZ | |

索引:`(run_id, step_index)`、`(run_id, case_index, step_index)`(计划报告按用例分组)、`(created_at)`(分区与清理用)。

**响应体分流**是这张表最重要的设计。≤ 64 KB 内联为 `bytea`(PG 默认 EXTENDED 存储会自动压缩,超过约 2 KB 自动 TOAST 到行外);> 64 KB 写 MinIO,表里只留对象 key。

**永远不要 `SELECT *` 这张表**。一次执行可能有上千行,每行的 body 可能是 64 KB。列表和统计查询必须显式列出需要的列。

**断言存 JSONB 而非独立表**。代价是无法直接做「某条断言的历史失败率」这类聚合查询。取舍理由:一次执行 1000 请求 × 5 断言 = 5000 行,独立表会让这张表再膨胀一个数量级,而断言级分析是低频需求。若日后确实需要,再加一张投影表,从 JSONB 回填。

**分区**:这张表是全库增长最快的。按 `created_at` 做**月度声明式分区**,保留策略直接 `DROP PARTITION`,不走 `DELETE`。分区键必须进主键,所以主键为 `(id, created_at)`。

## 10. 定时调度

### `schedule`

| 列 | 类型 | 说明 |

| id | BIGINT PK | |
| project_id | BIGINT FK→project | |
| name | VARCHAR(128) | |
| plan_id | BIGINT FK→test_plan | |
| cron_expression | VARCHAR(64) | 标准 5 段 cron(带秒的 6 段不支持) |
| timezone | VARCHAR(64) | IANA 时区名,如 `Asia/Shanghai` |
| enabled | BOOL | |
| environment_id | BIGINT FK→environment NULL | 覆盖计划的默认环境 |
| next_run_at | TIMESTAMPTZ NULL | tick 任务的查询依据;停用/软删时置空 |
| last_run_at | TIMESTAMPTZ NULL | |
| last_run_id | UUID NULL | **不建外键**(spec #35 决策 #11):纯展示指针,避免与 `run.schedule_id` 成循环外键 |
| last_skip_at | TIMESTAMPTZ NULL | 最近一次跳过时间(重叠/环境缺失等,只保留最近一次;tick 任务落值,issue #37) |
| last_skip_reason | TEXT NULL | 最近一次跳过原因,取值是稳定契约:`overlap` / `environment_missing` / `plan_empty` / `plan_deleted` / `project_deleted`(前端有中文映射) |

索引:`(enabled, next_run_at)`(tick 主查询)、`project_id`、`plan_id`。

**重算语义(spec #35 决策 #5)**:创建/启用/修改 cron 或时区 → 从当前时间重算 `next_run_at`;仅改名/改环境不重算;停用 → 置空。校验错误码 `cron_invalid` / `timezone_invalid`(cron 仅 5 段、时区须为合法 IANA 名称)。

**`next_run_at` 必须持久化**。tick 任务查 `WHERE enabled AND next_run_at <= now()`,而不是每次现算。现算需要扫描全部 schedule 并对每行求 cron 下一次时间,而持久化后这个查询走索引,且「上次跑到哪」有据可查。

**时区必须显式存储**。用 `Asia/Shanghai` 而非固定偏移量,因为偏移量不处理夏令时。cron 解释用 `croniter`,传入 tz-aware 的当前时间。

**重叠保护**:tick 派发前检查该 schedule 是否已有 `pending` / `running` / `stopping` 的 run。没有这层检查,一个跑 90 秒的任务配每分钟一次的 cron 会无限堆积。

## 14. 保留策略

平台的数据增长几乎全在两张表上。没有清理策略的话,半年后数据库会被历史执行记录压垮。

| 表 | 默认保留 | 方式 |
|---|---|---|
| `run` | 180 天 | 定期删除,保留有 `report_share` 的记录 |
| `run_step_result` | 90 天 | **`DROP PARTITION`** |
| `mock_request_log` | 7 天 | `DROP PARTITION` |
| `notification_log` | 30 天 | `DELETE` |
| `audit_log` | 365 天 | `DELETE` |
| MinIO 响应体对象 | 跟随 `run_step_result` | 先删对象再删行,或反向扫描孤儿对象 |

清理任务是 Celery 任务,跑在 `default` 队列,错开业务高峰。

**先删对象存储再删数据库行**,顺序不能反。反过来会先丢失「哪些对象该删」的信息,只能靠全量扫描找孤儿。
