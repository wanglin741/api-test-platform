# 阶段计划

> 2026-10-18 盘点:设计文档已定案但未实施的能力,按价值链与依赖排成五个阶段。一阶段展开到工单草案粒度,后续阶段随前一阶段收尾再细化。依据:[功能模块](功能模块.md)、[数据模型](数据模型.md)、[执行引擎](执行引擎.md)、[API设计](API设计.md) 的既有定案,本篇不重新设计,只做切分与排序。

## 1. 现状基线

已完成:

| 块 | 内容 |
|---|---|
| MVP 四页闭环 | 项目/环境/变量/用例 CRUD、DSL 执行引擎(http 步骤:变量替换/提取/断言/重试/超时/取消/fail_fast/总时长)、执行报告 |
| 平台化改版 | 调试工作台(#19)、目录树(#20)、报告详情改版(#21) |
| 实时进度 | SSE 事件流 + 断线续传/快照 + 轮询降级(#22–#27,含两轮评审修复) |
| 计划执行闭环(一阶段) | 计划 CRUD + 清单编排、串行/并行执行与失败即停、报告按用例分组、SSE 计划实时进度、报告按计划筛选(#28–#33) |
| 定时调度 + CI(二阶段) | 调度 CRUD 与 tick 派发、重叠跳过与 misfire、API Token 认证、幂等触发、质量门禁、JUnit 导出、前端调度/CI 面板(#35–#42) |

一句话缺口:**引擎表达力(条件/循环/嵌套/数据驱动)、通知与报告分享、Mock Server 均未建设** —— 批量、定时、CI 已闭环,执行结果可以进流水线,但还不能自己「写得复杂」、不能主动「喊人」、也测不了依赖外部接口的场景。

## 2. 排期总览

| 阶段 | 状态 | 主题 | 为什么在这个位置 |
|---|---|---|---|
| 一 | ✅ 2026-10-19 | **计划执行闭环** | 一切下游能力(定时/CI/通知/门禁)都挂在「计划」上;它是从「跑一条」到「管一批」的门槛,价值杠杆最大 |
| 二 | ✅ 2026-10-21 | 定时调度 + CI 集成 | 依赖计划;二者同阶段交付 —— 一个管「没人在场时跑」,一个管「跑完结果进流水线」 |
| 三 | 引擎表达力:`if` / `loop` / `case_ref` / 数据驱动 | 与二阶段可对调:先规模化(一~二)还是先表达力,取决于真实使用反馈;默认先规模化,因为没有定时回归的用例写法再花哨也没人看 |
| 四 | 通知与报告分享 | 依赖计划的 `run.failed`/`run.recovered` 事件语义;恢复通知需要「计划上次执行状态」,没有计划就没有稳定锚点 |
| 五 | Mock Server + 接口定义 | 独立价值线(挡板),与执行链解耦;独立进程 + 从接口定义生成规则是一大块,放最后 |

## 3. 一阶段:计划执行闭环

### 3.1 目标

用户能建一个计划(有序用例清单 + 执行配置),一键触发,在报告页实时看到多用例执行进度,终态看到计划级汇总与按用例分组的明细。完成后,二阶段的定时调度和 CI 触发只需在「触发来源」上做增量,不再动执行与报告内核。

### 3.2 范围(工单草案,tracer-bullet 纵切)

| # | 工单 | 交付的可演示行为 | 阻塞 |
|---|---|---|---|
| 1 | 计划 CRUD + 用例清单编排 | `test_plan`/`test_plan_item` 迁移;plans 端点(items 整体替换,API设计 §已定);前端计划列表/详情页(拖拽排序复用目录树/工作台的既有缝) | 无,可立即开始 |
| 2 | 串行计划执行 → 报告聚合展示 | 触发端点接受 `plan_id`;引擎串行跑完清单并逐步落库;报告详情按用例分组;可取消(复用既有协作点) | #1 |
| 3 | 并行与失败策略 + 实时进度定案 | `execute_mode=parallel`(`asyncio.gather` + `Semaphore(concurrency)`,执行引擎 §8 已定单任务内并行,不走 Celery canvas);`stop_on_fail`;SSE 在多用例下的实时进度 | #2 |
| 4 | 计划维度收口 | 报告列表按计划筛选(`run.plan_id` 索引已定);计划详情页挂最近执行入口;触发来源沿用 `manual`(服务端判定,**不新增 `plan` 取值**) | #2 |

### 3.3 spec 阶段必须先敲定的决策(已全部落定,2026-10-19 一阶段实施完毕)

1. **一次计划执行 = 一条 run 还是每用例一条 run?** → **定案:一条 run 承载整个计划**(spec #28)。`run_step_result` 补 `case_index`/`case_id`/`case_name` 用例维度列,报告/SSE 事件按用例归属扩展;单用例执行字段取缺省(`case_index` 0),既有消费方不变。
2. **SSE 事件载荷的多用例扩展** → **定案**:`step.*` 事件加 `case_index`/`case_name`(仅计划执行携带);`run.progress` 保持**步骤级全计划连续计数**(并行下用前置步数偏移保证 `completed` 唯一且推进到 total);前端步骤行 key 升级为 `(case_index, step_index)` 复合键,单用例(0, n)与旧形态兼容。
3. **summary 聚合口径** → **定案**:计划级 = 用例级求和(同一份字段形状),外加 `cases` 用例归属数组(含 skipped 用例 —— 它们没有步骤行);`pass_rate` 分母 = `total - skipped`(跳过不参与通过率,沿用单用例口径)。
4. **环境覆盖** → **定案**:触发请求体的 `environment_id` 覆盖 `plan.environment_id` 默认,两者都缺 → 422 `environment_required`。

顺路评估结论(§5 未决):报告列表本期只做**按计划筛选**(`plan_id` 查询参数 + 计划详情「最近执行」);按用例筛选暂不做 —— 单用例执行在列表已带 `#case_id` 列,真实需求出现再排。

### 3.4 验收

- 迁移含 `test_plan`/`test_plan_item`/`run.plan_id`;CRUD 与 items 整体替换过集成测试
- 串行/并行两种模式各自端到端集成测试(并行验证并发上限与 `stop_on_fail` 语义)
- SSE 在计划执行下:逐步实时、断线重连快照、终态收尾三条动线复用既有测试形态
- 前端:计划页 CRUD、触发跳报告、报告按用例分组 + 实时进度;type-check/lint/vitest 全绿
- 文档同变更:数据模型(API 触发请求体)、执行引擎(计划级并发已写,补实现定案)、前端设计(计划页)

### 3.5 明确不做(一阶段)

- 定时调度、CI、通知(二阶段及以后)
- 计划内嵌子计划(`item_type` 列保留但只允许 `case`,数据模型已注明)
- 计划级变量/数据驱动(引擎能力,三阶段)
- `retry_on_fail`/`retry_times`(计划级重试与用例级 retry 语义易混,等真实反馈;表列先建好)

## 4. 二阶段:定时调度 + CI 集成(已实施,2026-10-21)

### 4.1 目标

「没人在场时跑」(定时调度)与「跑完结果进流水线」(CI 触发 + 门禁 + JUnit 导出)同阶段闭环。工单 #36–#43,spec 见 #35。

### 4.2 spec 阶段敲定的决策(均已实施)

1. **触发来源服务端判定**:`trigger_mode` 不进请求体;无 Bearer → `manual`,API Token → `ci`(`triggered_by` 为空),调度 tick → `schedule`。不新增 `plan` 取值(修正一阶段遗留矛盾)。
2. **调度重算语义**:创建/启用/修改 cron 或时区重算 `next_run_at`;仅改名/改环境不重算;停用/软删置空。
3. **tick 派发**:beat 只注册一条每分钟 tick;扫 id 不加锁 + 逐条 `FOR UPDATE SKIP LOCKED` 重校验;重叠跳过不排队,原因落 `last_skip_reason` 稳定契约;misfire 以 now 为基准不补跑;beat 严格单实例。
4. **API Token 最小集**:只存 SHA-256 哈希、`at_` 前缀不透明串、scopes 默认 `run:trigger` + `report:read`;Token 仅允许 run 相关端点,其余一律 403 `token_not_allowed`;认证单入口 `resolve_principal`(SSE 同源)。
5. **幂等触发**:Redis pending(60s)/done(24h)两态 + fingerprint(`case_id`/`plan_id`/`environment_id`/`quality_gate` 参与规范化);同 key 不同 fingerprint → 409;重放 202 + `Idempotent-Replayed: true`;Redis 不可用 fail closed。
6. **质量门禁**:配置持久化 `run.quality_gate`,终态全路径求值写 `summary.gate_passed`,不改 `run.status`;未配置不写键;求值用精确通过率(与展示口径的四舍五入值区分);CI 退出码同时看 `status` 与 `gate_passed`(修正一阶段遗留矛盾)。
7. **JUnit 导出**:仅 `format=junit`,终态限定,只查轻量列不读响应体大字段;按用例分组的计划 run 映射为嵌套 `<testsuite>`。

### 4.3 验收(#43 收口记录)

- 后端:迁移重放(upgrade → downgrade → upgrade)、全量 pytest(含 import 边界检查 `tests/engine/test_boundary.py`)全绿
- 前端:type-check / lint / vitest / build 全绿
- 手工动线走查七条:到期自动跑、停用/启用重算、重叠跳过可见、Token + curl 触发、同 key 幂等重试、门禁标签、JUnit 导出可解析
- 文档终检:数据模型、API 设计、功能模块、架构设计、前端设计、开发环境/CLAUDE.md、术语表逐份与实现对齐

## 5. 后续阶段概要
- **三阶段 引擎表达力**:`if` 条件、`loop` 循环、`case_ref` 嵌套、数据驱动(`parameters_setting`,每轮迭代独立执行按 `parent_index` 归组)。依赖一阶段的 run 模型定案(数据驱动迭代与多用例的归属列可能同构)。
- **四阶段 通知与分享**:渠道(企微/钉钉/飞书/webhook/email,密钥加密)、规则(`run.failed`/`run.recovered`)、告警抑制(Redis 计数,30 分钟窗口)、报告分享 token(脱敏、可过期可撤销)。
- **五阶段 Mock Server + 接口定义**:独立 ASGI 进程、priority 顺序匹配、响应模板变量(`request.*`)、未命中 404 + 请求日志(7 天分区)、项目级限流;接口定义表 + 从 Schema 一次性生成 Mock 规则。

## 6. 未决问题

- 浏览器侧认证(JWT 登录页)不在任何阶段:CI 只要 API Token,浏览器免认证是前端设计 §1 的既定取舍,何时翻案看部署形态。
- 大响应体转对象存储(MinIO)未排期:观察到 PG 压力再做,不预建。
- 生产部署形态(compose 全量 / k8s)未排期:等真实部署需求,架构设计 §9 保持概要。
- 调度跳过历史只保留最近一次(`last_skip_at`/`last_skip_reason`):`audit_log` 表建表后可追溯全部,当前够用(功能模块 §2.3)。
- `callback_url` 回调端点未实现:API 设计已保留字段与契约,等真实 CI 场景提需求再排(轮询 + JUnit 已覆盖主流接入)。
