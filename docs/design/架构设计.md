# 架构设计

> 接口自动化测试平台 · 技术栈 FastAPI + Celery + Redis + PostgreSQL + Vue 3

## 1. 范围

平台提供接口功能自动化能力,外加 Mock Server、定时调度与 CI 集成、通知与报告分享。**不含性能压测** —— 压测的流量模型、指标采集和资源隔离诉求与功能测试完全不同,混在同一套 worker 里会互相干扰,留作后续独立演进。

用例以**可视化表单**为主要编写方式(前端配置请求、提取、断言),执行引擎为**自研异步引擎**,权限模型为**多项目 + RBAC**。

## 2. 进程拓扑

```
                    ┌──────────────┐
   浏览器 ──HTTP──▶ │  api         │  uvicorn × N   (async)
   CI ───Webhook──▶ │  FastAPI     │
                    └──┬────────┬──┘
                       │        │ send_task (run_in_threadpool)
              读/写    │        ▼
                    ┌──▼───┐  ┌─────────────┐
                    │ PG   │  │ Redis       │
                    └──▲───┘  │ · broker    │
                       │      │ · 进度流     │
                       │      │ · 取消标志   │
                       │      │ · 缓存       │
                       │      └──▲───────┬──┘
                       │         │       │
         ┌─────────────┴──┐  ┌───┴───────▼──────┐
         │ worker-exec    │  │ worker-default   │
         │ -Q execution   │  │ -Q default,      │
         │ 自研异步引擎    │  │    reports,      │
         │ (同步 Session) │  │    notify        │
         └────────────────┘  └──────────────────┘
                    ┌──────────────┐   ┌────────────┐
                    │ beat (单实例) │   │ MinIO      │
                    │ 每分钟 tick   │   │ 大响应体    │
                    └──────────────┘   └────────────┘
                    ┌──────────────┐
   Mock 流量 ──────▶ │ mock         │  独立 ASGI 进程
                    └──────────────┘
```

**为什么 mock 是独立进程**:Mock Server 的流量特征(高频、低延迟、面向外部调用方)与主 API(低频、重业务、面向登录用户)完全相反。跑在同一个 uvicorn 里会互相抢连接池和事件循环,而且 mock 需要独立的限流与 CORS 策略。代码上它与主应用共用同一份 `models` / `services`,只是 ASGI 入口和部署单元不同。

## 3. 分层

| 层 | 职责 | 关键约束 |
|---|---|---|
| **API 层** `app/api/` | REST 资源、SSE 进度流、鉴权与 RBAC | 只做校验与编排,**不执行测试**。所有耗时工作 `send_task` 出去 |
| **服务层** `app/services/` | 业务逻辑,事务边界 | 不依赖 FastAPI,可被 API / worker / mock 三方复用 |
| **执行引擎** `app/engine/` | 纯逻辑:DSL 解析、步骤执行、变量、断言 | **禁止 import FastAPI 或 Celery**。是一个可独立单测的库 |
| **任务层** `app/tasks/` | Celery 任务,薄封装 | 只做「加载 → 调引擎 → 落库」,不含业务规则 |
| **模型层** `app/models/` | SQLAlchemy 2.0 ORM | 全平台唯一 `Base` 与唯一 Alembic 迁移历史 |

`engine/` 与 `tasks/` 的分离是刻意的:引擎是最需要测试的部分,把它做成不依赖框架的纯函数库,才能用普通 pytest 快速覆盖,不必起 Celery 或 DB。

## 4. 关键决策

每条决策都标注了被否决的方案和理由。

### D1 · Celery 结果后端不承载业务结果

**决策**:`task_ignore_result = True`,执行结果全部写 PostgreSQL 业务表。Redis 只作 broker 与进度通道。

**理由**:Celery 官方文档对 Redis 后端的原话是「如果结果持久化重要,考虑用别的 DB 作为后端」,并列出键淘汰导致的 `InconsistencyError` 风险;`result_expires` 默认 1 天,昨天的报告可能直接消失。而执行记录本来就该落在 PG 里,再往结果后端存一份是纯粹的双写负担。

**代价**:失去 `AsyncResult.get()` 的便利,轮询任务状态要查自己的 `run` 表。这正是我们想要的 —— 前端本来就该查业务表。

### D2 · 自研异步执行引擎(httpx + asyncio)

**决策**:不用 pytest 作为执行内核。用 `httpx.AsyncClient` + `asyncio` 自建。

**理由**:平台需要**步骤级**的结构化报告(每步的请求、响应、耗时、变量提取结果、每条断言的通过情况)。pytest 的输出是为终端设计的,要映射成这套结构得写一层脆弱的适配。自研引擎对每一步完全可控。参照物:MeterSphere 自研 DSL 编译成 JMX,HttpRunner 自研解释器,zerorunner 明确 fork 了 HttpRunner 的解释器 —— 成熟平台无一例外自研。

**代价**:pytest 生态的现成能力(fixture、插件、IDE 调试)用不上。这部分能力通过 YAML/代码导入导出补偿,而不是通过复用 pytest 运行时。

### D3 · 取消:持久化的带外信号 + 协作式轮询

**决策**:取消**不是** Celery 的 `revoke`。流程为:

1. `POST /runs/{id}/cancel` 先写 `run.cancel_requested_at` 并 `SET run:cancel:{id} 1 EX 3600`,**再**改 `run.status = stopping`
2. worker 在**步骤之间、数据驱动迭代之间、CSV 行之间**轮询该 Redis key(间隔 0.2s)
3. 检测到取消 → 剩余步骤标记 `skipped`,汇总后置 `status = stopped`
4. 兜底:`task_soft_time_limit` 到点抛 `SoftTimeLimitExceeded` 做清理;`task_time_limit` 硬杀进程

**理由**:这是调研中同类平台最普遍的缺陷。6 个 Python 项目里 3 个完全没有取消;1 个只写 DB 标志位而 worker 随后用 `COMPLETED` 覆盖它;1 个用进程内 `set` + `Lock`,在单进程单 worker 下正确,一旦扩容或加 worker 就静默失效。Celery 文档本身也说 `revoke(terminate=True)` 「绝不能以编程方式调用」—— 它杀的是 worker 子进程,可能误杀同进程内其他任务。

**为什么必须有 `stopping` 状态**:从发出取消到 worker 真正停下之间有窗口,若直接置 `stopped`,UI 和 DB 会在这个窗口里互相矛盾。

**为什么先写取消标志再改状态**:否则存在竞态 —— worker 可能在状态已改但标志未写时读到一个空标志继续跑。

### D4 · 大响应体不进 OLTP 库

**决策**:响应体按大小分流。**小于 64 KB** 直接存 `run_step_result.response_body`(`bytea`,PG 默认 EXTENDED 存储,自动压缩);**超过 64 KB** 写入 MinIO,表里只留 `object_key` + `sha256` + `size_bytes` + `truncated`。

**理由**:PG 单字段上限 1 GB,超过约 2 KB 触发 TOAST 拆成 ~2000 字节的行,单条记录本身很便宜但**读取很贵**。同类项目的教训很直接:MeterSphere 把响应体存成 MySQL `LONGBLOB` 并需要专门 sweeper 清理,RunnerGo 塞进 Mongo 文档并报告长跑冲突。会把库撑爆的东西不该放在库里。

**代价**:「DB 行 + 对象」变成一对需要手动维护一致性的记录。用保留策略任务定期清理孤儿对象,并在报告页对已过期的 body 显示占位而非报错。

**配套**:默认只存响应体前 N KB(可配置),「存储完整响应体」是每个项目级的显式开关。

### D5 · 定时调度用 tick 任务,不用 beat 动态注册

**决策**:调度定义存在自己的 `schedule` 表。Celery beat 里只注册**一条**每分钟执行的 `dispatch_due_schedules` 任务,它查表找出到期项并派发执行。

**理由**:beat 默认的 `PersistentScheduler` 把上次运行时间存在本地 shelve 文件里,API 进程对 `beat_schedule` 的修改它根本感知不到;多实例还会重复触发(官方明确警告「必须确保同一调度只有一个 scheduler 在跑」)。非 Django 生态没有第一方 DB 调度器,只有 RedBeat / celery-sqlalchemy-scheduler 这类第三方。tick 方案把「什么该跑」留在自己的领域模型里,cron 语义显式且可单测,同时绕开了 beat 单实例锁的问题。

**配套**:cron 任务可能重叠(上次没跑完下次又到点),派发前要检查该 schedule 是否已有 `running` 中的 run,或加分布式锁。

### D6 · worker 用同步 Session,API 用 async Session

**决策**:API 进程用 `create_async_engine` + `asyncpg`;worker 进程**全程同步** `Session` + `psycopg`,只有 HTTP 请求那一段是 async(`asyncio.run` + `httpx.AsyncClient`)。

**理由**:SQLAlchemy 文档明确警告 `AsyncEngine` 不能跨事件循环复用 ——「把 `AsyncEngine` 从一个事件循环传到另一个…可能抛 `Task got Future attached to a different loop`」。而 prefork worker 会在长生命周期进程里反复 `asyncio.run()`,模块级 async engine 是地雷,且这类错误只在负载下间歇出现。worker 里用同步 Session 直接绕开整个问题。

**注意**:`AsyncClient` 和 engine 必须在协程**内部**创建,不能放在模块导入期。

### D7 · 可执行用例是版本化 JSON 文档,另加投影表

**决策**:用例的完整定义(步骤树、提取、断言、变量)存成一份 JSON 文档,是执行的唯一事实来源;`run_step_result` 只作为**执行结果的投影**存查询需要的字段(步骤序号、类型、状态、耗时、通过/失败),用于列表页和聚合统计。

**理由**:这是同类项目收敛出的设计。JSON 文档便于版本快照、diff 和整体下发给 worker;投影表让「最近 7 天失败率最高的用例」这类查询不必扫 JSON。反面教材是 MeterSphere 用 `version_id`/`ref_id`/`latest` 做**行复制式版本管理**,定义表被乘法级膨胀;RunnerGo 的 `target` 表把 folder/api/group/scene/case 五种实体塞进一张表;以及某项目的 `case_list` 用逗号分隔 TEXT 存 ID。

## 5. Celery 配置

```python
celery_app.conf.update(
    task_routes={
        "engine.execute_run":     {"queue": "execution"},
        "reports.*":              {"queue": "reports"},
        "notify.*":               {"queue": "notify"},
        "maintenance.*":          {"queue": "default"},
        "*":                      {"queue": "default"},
    },
    task_queues=(Queue("default"), Queue("execution"), Queue("reports"),
                 Queue("notify")),

    # 执行任务是长任务且有副作用
    task_acks_late=True,
    task_reject_on_worker_lost=True,   # 依赖任务幂等,见下
    worker_prefetch_multiplier=1,      # 每个进程只预取一个任务
    worker_disable_prefetch=True,      # 5.6+,仅 Redis broker,彻底消除队头阻塞
    worker_soft_shutdown_timeout=30,   # 5.5+,SIGTERM 时排空在途任务

    task_soft_time_limit=55 * 60,      # 可捕获 SoftTimeLimitExceeded 做清理
    task_time_limit=60 * 60,           # 硬杀并替换 worker 进程

    task_ignore_result=True,
    task_store_errors_even_if_ignored=True,
    broker_url=f"{REDIS}/1",
    result_backend=None,
)
```

**执行任务必须幂等**,因为 `acks_late` + `task_reject_on_worker_lost` 意味着 worker 崩溃后任务会被重投。任务入口先检查 `run.status`,已经是终态就直接返回;重跑前清空该 run 已有的 `run_step_result`。

**`worker_prefetch_multiplier=1` 的语义**:官方文档说明这是让 worker「一次只保留一个任务」的推荐方式。默认值 4 会让一个 10 分钟的执行任务堵住后面几十个小任务。

**并发度**不由 Celery 决定。worker 用 prefork 池(默认推荐,且绿色线程池会静默禁用 `soft_time_limit`),单个执行任务内部用 `asyncio.Semaphore` 控制对目标服务的并发请求数 —— 这个值是可配置的,因为它取决于被测服务能扛多少压力。

**不用 eventlet**:upstream eventlet 已发布「Migrating off of Eventlet」指南,自述不再鼓励新用户,并点名 Celery 这类「可插拔后端」用法「根本不可持续」。

## 6. 实时进度推送

> **已实现**(issue #22 系列):事件名常量模块、Stream 发布器、SSE 端点、前端订阅均已落地,见 `app/event_names.py`、`app/run_events.py`、`app/api/v1/runs.py`。

**通道**:Redis Streams(`XADD` / `XREAD BLOCK`),而非 Pub/Sub。

**理由**:Pub/Sub 是至多一次投递,客户端在消息发布时没订阅就永远看不到。用户刷新页面、网络抖动、或打开一个已跑了 30 秒的执行,都会丢事件。Streams 支持按 ID 重放,配合 SSE 的 `Last-Event-ID` 头可以无缝续传。单次执行的完整历史另有 PG 兜底。

**事件归属**(语义定案):**引擎只发逐步事件**(step.started / step.finished / run.progress,引擎是唯一知道逐步事实的地方);**执行级事件归任务层**(run.started / run.finished —— started_at 是数据库时间、summary 含断言统计,只有任务层掌握这些事实)。`run.snapshot` 由 SSE 端点在读数据库后发出,是客户端重新同步的唯一入口。

**事件类型**:

| 事件 | 发射方 | 载荷 |
|---|---|---|
| `run.started` | 任务层 | `{total_steps, started_at}`(started_at 取数据库 `now()`) |
| `step.started` | 引擎 | `{step_index, step_name, step_type}`(构建成功、真正发请求前;跳过与构建失败没有「开始」,重试不重发) |
| `step.finished` | 引擎 | `{step_index, step_name, status, duration_ms, assertion_total, assertion_passed}`(字段对齐落库列) |
| `run.progress` | 引擎 | `{completed, total}`(**限流至 1/s,限流在发布器**) |
| `run.finished` | 任务层 | `{status, summary}`(summary 与报告详情接口同一份) |
| `run.snapshot` | SSE 端点 | `{run, steps, steps_truncated}`(从数据库读出的当前完整状态) |

**流定案**:流键 `run:events:{run_id}`(与取消键 `run:cancel:{id}` 同构);`XADD MAXLEN ~ 10000` 裁剪大小;每次发布续期 24h,终态后降到 1h —— 封住「worker 被强杀、永不发终态」的孤儿流生命周期。Redis 里的一切可从数据库重建,所以裁剪与过期可以激进。**发布失败一律吞掉并记 warning**:事件通道只是进度展示,执行与报告落库不依赖它。run.progress 的 1 秒限流是发布器的**投递策略**而非引擎逻辑(`completed == total` 恒放行),引擎单测因此保持确定性。

**端点**:`GET /api/v1/runs/{id}/events`,SSE。FastAPI 0.135.0 起原生支持(`from fastapi.sse import EventSourceResponse`),不再需要 `sse-starlette`。起点判定:无 `Last-Event-ID`、流为空、或游标(按「毫秒-序号」数值比较)早于流首 ⇒ 快照路径(先取流尾再读数据库);游标仍有效 ⇒ 从游标后重放。连续空读约 60 秒查一次库,已终态而流里没有终态事件则补发并关闭。端点不持有数据库连接:认证与 404 在流开始前用短会话完成(yield 依赖会把连接占住整个 SSE 生命周期)。

**写入策略**:`run_step_result` 每步一行写 PG(这是事实来源,必须落);进度经 Stream 推送,限流在发布器。绝不把 Celery 的 `update_state` 当日志用 —— 它的实现就是每次调用全量写一遍结果后端,单次执行上千个请求就是上千次后端写。

**降级**:SSE 连不上时前端退化为 2 秒轮询 `GET /runs/{id}`。这个接口本来就存在,不需要额外实现。

## 7. 数据存储职责划分

| 存储 | 存什么 | 不存什么 |
|---|---|---|
| **PostgreSQL** | 项目、环境、变量、接口定义、用例 DSL、套件、计划、执行记录、步骤结果、报告、调度、通知、RBAC、Mock 规则 | 大响应体、临时进度 |
| **Redis** | Celery broker、进度 Stream、取消标志、热缓存、分布式锁 | 任何不可重建的数据 |
| **MinIO** | 超限响应体、附件、导出报告 | 需要事务一致性的数据 |

**Redis 里的一切都必须可重建。** 它是缓存和消息通道,不是存储。这条规则让 Redis 可以随时 flush 而不丢数据。

## 9. 部署形态

开发环境用 `docker compose` 起 PG / Redis / MinIO,应用进程本地跑以便热重载。生产环境每个进程类型独立伸缩:

| 服务 | 实例数 | 伸缩依据 |
|---|---|---|
| `api` | N | 请求量,无状态可任意扩 |
| `worker-exec` | N | 待执行队列长度 |
| `worker-default` | 1~2 | 报告与通知量 |
| `beat` | **严格 1** | 不可水平扩展,多实例会重复派发 |
| `mock` | N | Mock 流量,无状态 |

**beat 必须单实例**是硬约束。tick 方案已经把「重复派发」的风险降到最低(只有一条 tick 任务),但 tick 本身仍不能并发跑两个。

## 10. 未决问题

这些在写详细设计前需要定,当前文档不做假设:

- **脚本断言沙箱**:是否提供 JS 断言。若提供,必须用 QuickJS/WASM 沙箱,不能用 Node `vm` —— Hoppscotch 曾因 `vm` 沙箱逃逸导致 RCE(CVE-2024-34347)。
- **分布式执行节点**:当前设计假设 worker 与 API 共享数据库。若要支持「部署到客户内网的执行机」,需要引入 MeterSphere 那样的资源池抽象,复杂度显著上升。
- **测试数据集存储**:数据驱动的大 CSV 放 PG 还是 MinIO,取决于预期规模。
