# 功能模块设计

> Mock Server · 定时调度与 CI 集成 · 通知与报告分享

## 1. Mock Server

### 1.1 为什么是独立进程

Mock 的流量特征与主 API 完全相反:

| | 主 API | Mock |
|---|---|---|
| 消费者 | 平台用户 | 被测系统 |
| QPS | 低 | 高,且不可预测 |
| 延迟要求 | 宽松 | 严格(它是被测链路的一环) |
| 认证 | JWT / API Token | 项目级 Mock Token,或免认证 |
| 错误格式 | 平台统一格式 | **必须伪装成真实第三方接口** |
| 日志保留 | 长 | 短(7 天) |

跑在同一个 uvicorn 进程里,一次 Mock 流量洪峰会占满连接池和事件循环,主 API 跟着一起不可用。因此 `app/mock/main.py` 是独立的 ASGI 入口,部署为独立服务,与主应用**共用 `models` / `services`**,只是进程和路由不同。

### 1.2 匹配算法

```
按 priority 升序排列该项目所有 enabled 规则
逐条检查 method / path / conditions
首个全部命中的规则胜出
```

**不做「最具体匹配」的自动推导**。那类规则(路径越长越优先?正则比前缀优先?)用户无法预测,最终会变成「为什么我的规则没生效」的反复排查。显式的 `priority` 数字虽然笨,但行为完全可预测 —— 这正是 Mock 工具最需要的性质。

`priority` 默认值取**创建顺序的倒数**,即新建规则默认优先级最高。这符合直觉:用户新建一条规则通常是为了覆盖已有行为。

### 1.3 匹配维度

**路径匹配**:

| `match_type` | 语义 | 示例 |
|---|---|---|
| `exact` | 全等 | `/api/users` 只匹配 `/api/users` |
| `prefix` | 前缀 | `/api/users` 匹配 `/api/users/1` |
| `regex` | 正则 | `^/api/users/\d+$` |

**`conditions` 条件匹配**(全部满足才算命中):

```json
{
  "query":  { "page": "1" },
  "headers": { "X-Env": "test" },
  "body_jsonpath": { "$.type": "vip" },
  "body_contains": "premium"
}
```

每个维度内部是「全部键值相等」的与关系。**不提供正则条件** —— 需要正则的场景用路径级 `regex` 配合多条规则表达,保持条件模型简单。

### 1.4 响应构造

| 字段 | 说明 |
|---|---|
| `response_status` | 状态码 |
| `response_headers` | 响应头,含 `Content-Type` |
| `response_body` | 响应体文本 |
| `delay_ms` | 人为延迟,用于模拟慢接口 |

**响应体支持模板变量**,从请求中提取后回显:

```
{"id": "{{request.query.id}}", "name": "{{request.body.name}}", "ts": {{$timestamp}}}
```

可用的取值来源:`request.query.*`、`request.headers.*`、`request.body.*`(JSONPath)、`request.path.*`。

这让 Mock 能对「创建后查询」这类流程给出合理响应,而不必为每条数据写一条规则。**这是 Mock 可用性的分水岭** —— 固定响应的 Mock 在第三个接口就会失效。

### 1.5 从接口定义生成 Mock

`api_definition.response_schema`(JSON Schema)可以一键生成 Mock 规则,响应体按 Schema 生成符合结构的示例数据。

生成规则是**一次性的快照**,不是活的绑定 —— 生成后接口定义再变,Mock 规则不会自动跟着变。需要时重新生成,并提示会覆盖手工修改。活绑定听起来更好,但会让「我明明改了 Mock 响应为什么不生效」变成一个高频困惑。

### 1.6 未命中处理

未命中任何规则时:

- 返回 **404**,响应体是项目级可配的兜底内容(默认 `{"error": "no mock rule matched"}`)
- 记入 `mock_request_log`,`matched: false`

**不返回平台的标准错误格式**。Mock 端点的响应会被被测系统当作真实响应解析,平台格式会污染被测系统的解析逻辑。

`mock_request_log` 里未命中的记录是排查的唯一依据 —— 用户看到的只是「接口返回 404」,需要能查到实际请求的 method/path/headers/body 才能知道为什么没匹配上。

### 1.7 部署与限流

- 独立进程,可独立伸缩
- 项目级 QPS 限流,默认 1000
- `mock_request_log` 按天分区,保留 7 天

**限流必须存在**:被测系统在测试失败时往往有重试逻辑,一个配置错误的 Mock 规则会引发重试风暴。没有限流,平台会被自己的被测系统打垮。

## 2. 定时调度

### 2.1 调度模型

```json
{
  "name": "每晚回归",
  "plan_id": 12,
  "cron_expression": "0 2 * * *",
  "timezone": "Asia/Shanghai",
  "environment_id": 5,
  "enabled": true
}
```

`cron_expression` 是标准 5 段 cron(分 时 日 月 周),用 `croniter` 解释。

**时区必须显式存储且用 IANA 名称**(`Asia/Shanghai` 而非 `+08:00`)。固定偏移量不处理夏令时,而跨时区团队是常态。

### 2.2 tick 派发机制

Celery beat 里**只注册一条**每分钟执行的任务:

```python
@celery_app.task
def dispatch_due_schedules():
    now = utcnow()
    due = session.query(Schedule).filter(
        Schedule.enabled == True,
        Schedule.next_run_at <= now,
    ).with_for_update(skip_locked=True).all()

    for s in due:
        if has_active_run(s):        # 重叠保护
            s.next_run_at = compute_next(s, now)
            continue
        run = create_run(s)
        celery_app.send_task("engine.execute_run", args=[str(run.id)], queue="execution")
        s.last_run_at, s.last_run_id = now, run.id
        s.next_run_at = compute_next(s, now)
    session.commit()
```

**为什么不用 beat 的动态调度**:beat 默认的 `PersistentScheduler` 把上次运行时间存在本地 shelve 文件里,API 进程对 `beat_schedule` 的修改它根本感知不到;多实例还会重复触发。非 Django 生态没有第一方 DB 调度器。tick 方案把「什么该跑」留在自己的领域模型里,语义显式且可单测。

`with_for_update(skip_locked=True)` 让多个 beat 实例(误配时)不会派发同一行。

### 2.3 重叠保护

派发前检查该 schedule 是否已有 `pending` / `running` / `stopping` 的 run。

没有这层保护,一个跑 90 秒的计划配每分钟一次的 cron 会无限堆积执行记录,并持续占用 worker 槽位,最终拖垮整个执行队列。

**重叠时的行为是「跳过本次,不排队」**,并记录一条审计日志。跳过的信息应该在调度详情页可见 —— 用户需要知道「我的任务因为上次没跑完而跳过了」,而不是对着执行记录的空档困惑。

### 2.4 错过执行(misfire)的处理

平台停机 8 小时后重启,这段时间内到点的调度怎么办?

| 方案 | 后果 |
|---|---|
| 逐个补跑 | 停机 8 小时 × 每分钟一次 = 补跑 480 次,重启瞬间打垮 worker |
| 只补跑最近一次 | 折中,但语义含糊 |
| **跳过,只算下一个未来时间点** ← 采用 | 简单、可预测 |

选跳过的理由:接口测试的定时执行是**定期体检**,不是事件处理。补跑一次两小时前的体检没有任何价值 —— 被测系统的状态早已改变,补出来的结果反而是误导。而补跑带来的雪崩风险是真实的。

实现上很简单:`compute_next` 从 `max(next_run_at, now)` 开始算,**不遍历中间错过的时间点**。

这是一个容易被忽略但后果严重的点。任何引入补跑逻辑的设计都需要先回答「为什么两小时前的测试结果对现在有价值」。

### 2.5 启用/停用

停用不删除记录。停用后 `next_run_at` 置 NULL,tick 查询自然跳过(`next_run_at <= now` 对 NULL 为假)。

重新启用时**从当前时间重新计算** `next_run_at`,不追溯停用期间的时间点。

## 3. CI 集成

### 3.1 接入方式

| 方式 | 适用 |
|---|---|
| REST + API Token | 通用,任何能发 HTTP 的 CI |
| JUnit XML 报告 | 需要把结果并入 CI 测试报告的场景 |
| `callback_url` 回调 | 需要在测试完成后触发后续步骤 |
| Webhook 触发 | GitLab / GitHub 的 push / MR 事件 |

### 3.2 典型流水线

```bash
# 1. 触发执行,拿到 run_id
RUN_ID=$(curl -sS -X POST "$PLATFORM/api/v1/projects/1/runs" \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $CI_PIPELINE_ID" \
  -d '{"plan_id": 12, "environment_id": 5, "trigger_mode": "ci"}' \
  | jq -r .run_id)

# 2. 轮询直到终态
while true; do
  STATUS=$(curl -sS "$PLATFORM/api/v1/runs/$RUN_ID" \
    -H "Authorization: Bearer $API_TOKEN" | jq -r .status)
  case "$STATUS" in
    success) exit 0 ;;
    failed|error|stopped) exit 1 ;;
  esac
  sleep 5
done
```

**`Idempotency-Key` 用流水线 ID 而非随机值**。CI 重试同一构建时不会产生重复执行记录。

**轮询间隔 5 秒**。SSE 更适合浏览器场景,CI 脚本用轮询更简单可靠(不需要处理重连)。

### 3.3 质量门禁

CI 关心的不只是「有没有失败」,还有「通过率是否达标」。请求体支持:

```json
{
  "plan_id": 12,
  "quality_gate": {
    "min_pass_rate": 0.95,
    "max_error_count": 0
  }
}
```

不达标时 run 状态仍是 `success`(测试确实跑完了),但 `summary.gate_passed: false`。CI 脚本据此判断退出码。

**门禁结果不改变 run 状态**是刻意的:把「测试执行成功」和「质量达标」混成一个状态,会让报告失去区分能力 —— 用户无法知道到底是没跑成还是没达标。

### 3.4 与 OpenAPI 生成用例的关系

平台的 OpenAPI 文档(`/api/v1/openapi.json`)可以生成 CI 用的客户端,但**首版不提供官方 CLI**。curl + jq 的脚本足够,且不引入需要维护的额外分发渠道。若 CI 集成成为高频需求,再考虑 CLI。

## 4. 通知与报告分享

### 4.1 通知渠道

| `type` | 实现 |
|---|---|
| `webhook` | 通用 HTTP POST,自定义 JSON 模板 |
| `wecom` | 企业微信机器人 |
| `dingtalk` | 钉钉机器人 |
| `feishu` | 飞书机器人 |
| `email` | SMTP |

**密钥加密存储**。渠道配置里的 webhook URL / token 必须加密后入库(与变量不同 —— 变量是用户自己的测试数据,渠道密钥是平台的集成凭据)。API 返回时一律脱敏为 `***`。

### 4.2 触发规则

```json
{
  "name": "回归失败告警",
  "channel_id": 3,
  "events": ["run.failed", "run.recovered"],
  "scope": { "plan_ids": [12, 15] },
  "enabled": true
}
```

| 事件 | 触发条件 |
|---|---|
| `run.failed` | 终态为 `failed` 或 `error` |
| `run.recovered` | 本次成功**且**该计划上次是失败 |
| `run.finished` | 任何终态 |
| `run.stopped` | 被取消 |

`scope` 支持 `{"all": true}` 或显式列出 `plan_ids` / `schedule_ids`。

**`run.recovered` 需要查该计划的上一次执行状态**,是规则求值里唯一的跨记录查询。恢复通知很有价值 —— 否则用户只知道「一直在告警」,不知道什么时候好了。

### 4.3 告警风暴抑制

一个每 5 分钟执行一次的计划,如果持续失败,一天会产生 **288 条通知**。没有人会看,而且很快会把渠道拉黑。

抑制策略:

1. **同一计划 + 同一事件类型的连续失败,在 N 分钟内只发首条**(默认 N = 30)
2. 抑制期间的通知累计计数
3. 抑制窗口结束时,若累计数 > 1,发一条汇总:「该计划在过去 30 分钟内失败 6 次」

实现:Redis key `notify:suppress:{plan_id}:{event}` 带 TTL,值为累计计数。

**这是通知功能能不能用的关键**。没有抑制的告警系统会迅速被用户关闭,然后真正的问题也没人看到。

### 4.4 消息模板

默认模板包含:项目名、计划名、状态、通过/失败数、通过率、耗时、报告链接。

**报告链接必须是可访问的**。定时和 CI 触发的执行没有登录用户,若链接指向需要登录的页面,收到通知的人点进去是登录页。因此通知里的链接使用**分享 token**(见 §4.5),而不是内部路由。

webhook 类型支持自定义 JSON 模板,用与 Mock 相同的 `{{var}}` 语法。

### 4.5 报告分享

```
POST /runs/{rid}/share
→ 201 { "token": "rsh_abc123...", "url": ".../share/rsh_abc123...", "expires_at": "..." }
```

| 属性 | 说明 |
|---|---|
| `expires_at` | 可空。NULL 表示永久 |
| 密码保护 | 可选,分享链接需要额外输入访问码 |
| 可撤销 | 删除记录即失效 |

**分享页面只读,且只暴露报告内容** —— 不包含项目导航、其他用例、环境变量值等。分享链接会流到企业微信群里,必须假定它是半公开的。

**分享页面必须脱敏**:`is_secret` 变量的值、请求头里的 `Authorization`、响应头里的 `Set-Cookie` 一律替换为 `***`。这是报告脱敏规则的延伸 —— 分享场景下它更重要,因为受众超出了项目成员范围。

### 4.6 报告内容

一份报告包含:

1. **汇总**:状态、通过率、用例数、断言数、总耗时
2. **用例列表**:每条用例的状态、耗时、失败断言数,可展开
3. **步骤明细**:请求(method / URL / 头 / 体)、响应(状态码 / 头 / 体)、耗时、提取的变量、每条断言的通过情况
4. **失败聚焦**:默认展示失败项,一键过滤

**步骤明细默认折叠,失败项默认展开**。一次执行 1000 步全展开,浏览器会卡死,而且用户 95% 的时间只看失败的那几条。

### 4.7 导出

| 格式 | 用途 |
|---|---|
| HTML | 单文件离线报告,内嵌 CSS 与截图 |
| JUnit XML | 并入 CI 测试报告 |

**导出 HTML 时响应体一律截断**到 10 KB/步。一份包含 1000 步完整响应体的 HTML 文件会有几十 MB,浏览器打不开,邮件发不出。离线报告的价值在于「能看」,不在于「数据全」。

完整数据始终可以在平台的报告页查询,导出的定位是快照和分享。
