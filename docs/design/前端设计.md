# 前端设计(MVP)

> `frontend/` · Vue 3 + TypeScript + Vite + Pinia + Vue Router。第一阶段(spike #1)验证了引擎与执行管道,本篇定义第一条可视化闭环的形态。来源:grilling 第二阶段三轮对齐(全部按推荐项锁定)。

## 1. 范围

**做**(spec user stories 1–20 的 UI 化,四页闭环):

| 页面 | 能力 |
|---|---|
| 环境与变量 | 环境列表 + 环境级/项目级变量管理;`is_secret` 值打码,点眼睛临时显示 |
| 用例管理 | 用例列表 + DSL 编辑器 + 保存(保存即产生新版本) |
| 触发执行 | 选环境触发(202)→ 跳转报告详情;运行中可取消 |
| 执行报告 | 报告列表(回看历史)+ 详情(汇总、步骤时间线、请求/响应快照、断言明细) |

**不做**:登录页(后端免认证,种子用户)、结构化 DSL 表单(先让用户写原生 JSON 反哺 DSL 设计)、Playwright e2e、SSE(轮询)、项目管理独立页(只做选择器 + 新建弹窗,删改走 Swagger)。

## 2. 技术选型

| 项 | 选型 | 理由 |
|---|---|---|
| 组件库 | Element Plus | 重表格重表单的 admin 形态,中文生态最成熟,无需设计投入 |
| HTTP | `openapi-fetch` + `openapi-typescript` | 与后端自动生成的 OpenAPI 文档直连,类型零手工同步(API设计 §9) |
| DSL 编辑 | CodeMirror 6 + `@codemirror/lang-json` | 轻量、JSON 语法校验成熟 |
| 测试 | Vitest + jsdom + @vue/test-utils | 与 Vite 同族;两条缝见 §7 |
| 状态 | Pinia(已装) | store 承载全部业务逻辑,组件薄 |

**开发代理**:Vite dev server 把 `/api` 代理到 `http://127.0.0.1:8000`,免 CORS;生产部署形态不在本篇范围。

## 3. 类型生成流程

后端 FastAPI 自动产出 `/api/v1/openapi.json`(每个端点显式 `response_model` + `status_code`,错误写进 `responses` —— 这是后端契约,见 API设计 §9)。前端:

```
npm run gen:api   # 后端在跑时执行:拉 openapi.json → openapi-typescript → src/api/schema.d.ts
```

- `schema.d.ts` **提交进仓库**:类型变了在 code review 里可见。
- 后端改了响应结构而前端未重新生成 → `openapi-fetch` 的类型与运行时不符,type-check 未必能全拦;MVP 靠约定(后端改响应的 PR 必须附带重新生成),CI 校验留到有 CI 时补。

## 4. 布局与路由

经典 admin 布局:**左侧固定 sidebar** + **顶栏项目选择器**。

| 路由 | 页面 |
|---|---|
| `/cases` | 用例列表(默认首页) |
| `/cases/:id` | 用例编辑(CodeMirror) |
| `/environments` | 环境与变量 |
| `/runs` | 报告列表 |
| `/runs/:id` | 报告详情 |

**项目切换**:当前项目 id 存 Pinia 全局 store(持久化到 localStorage),顶栏选择器切换后整站数据重取;无项目时引导先创建。新建项目走顶栏弹窗(名称 + 描述)。

## 5. 状态层

每个资源一个 store,store 是唯一的业务逻辑所在(组件只做展示与事件转发):

- `projectStore`:项目列表、当前项目 id。
- `environmentStore` / `variableStore` / `caseStore`:各自资源的列表与 CRUD 状态。
- `runStore`:触发、轮询(run + steps 两个轮询合并:steps 变更时才重取)、取消。

API client 通过 store 的工厂函数注入,测试时换 mock 实现 —— 与后端「EngineContext 注入」同构,这是 store 缝可测的前提。

## 6. 执行与报告动线

1. 用例编辑页「执行」→ 弹窗选环境(必选,默认上次用的)→ `POST /projects/{pid}/runs`(202)→ 路由跳 `/runs/{run_id}`。
2. 报告详情每 **2s** 轮询 `GET /runs/{rid}` + `GET /runs/{rid}/steps`;run 到终态(`RUN_TERMINAL_STATUSES`)停轮。轮询逻辑在 `runStore`,组件不感知。
3. 运行中顶部状态条:状态、已耗时、「取消」按钮(→ `POST /runs/{rid}/cancel`)。
4. 步骤时间线:每步状态/耗时/断言通过数,展开看请求/响应快照(含截断标记)与提取到的变量;skipped 步骤显示原因。

## 7. 测试策略(两条缝)

与后端「引擎缝 + 应用缝」同思路——业务逻辑在 store,组件测试只钉关键渲染:

| 缝 | 测什么 | 手段 |
|---|---|---|
| **缝 1:Pinia store** | 注入 mock API client,验证状态迁移:列表加载/错误、**轮询启停**(终态停轮、取消后停轮)、CRUD 后列表刷新 | Vitest + mock client,毫秒级 |
| **缝 2:关键组件挂载** | 报告步骤时间线渲染(含截断/断言失败态)、DSL 编辑器校验错误回显、`is_secret` 打码切换 | @vue/test-utils |

不测:Element Plus 自身行为、纯展示模板。不引入 Playwright(页面稳定后评估)。

## 8. 错误处理约定

- `openapi-fetch` 外包一层 client 工厂,统一拦截错误响应:后端格式恒为 `{"error":{code,message,details}}`,非 2xx → ElMessage 弹出 `message`(开发模式附 `code`)。
- DSL 保存校验:前端只查 JSON 语法(CodeMirror 错误标线);**业务校验全交给后端** `parse_dsl` —— 400 时把 `details` 的字段定位回显在编辑器上方。不引 ajv/JSON Schema:pydantic 导出 schema 给前端是双份真相,违背单一来源。

## 9. 未决问题

- 报告列表要不要按用例筛选(端点暂无 filter 参数)—— 等真实使用反馈。
- CI 中的 schema 同步校验(npm script 比对自己重新生成的 diff)—— 有 CI 后补。
- 结构化 DSL 表单 —— 等 JSON 编辑器攒到用户反馈再设计。
